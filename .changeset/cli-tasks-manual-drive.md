CLI: manual MCP Tasks loop matching the Inspector Tasks tab. New commands `tasks capabilities | get | list | result | cancel | update | watch`, plus `tools call --task` / `--task-watch` (with `--task-ttl`, `--wire`, and watch-tuning flags) driving a created task to a terminal status over one connection on both the legacy 2025-11-25 wire and the SEP-2663 extension wire. Watch exit codes: 0 completed, 6 input-required, 7 timeout, 130 aborted, 1 otherwise.

SDK (additive): task manual-drive surface re-exported at the package root — `LEGACY_TASK_STATUSES`, `canDeclareTasksExtension`, `readDeclaredInputCapabilities`, `TaskInputRejectedError`, `DEFAULT_TASK_INPUT_LIMITS`, `createStrictElicitationContentValidator` (the strict dialect-aware elicitation self-validation rule the manager's MRTR path uses, as a shared factory), `retryAfterMsFromError`, and the associated types. The CLI statically imports these exports, which do not exist in published 2.0.x — coupling both packages in this changeset makes `changeset version` (via `updateInternalDependencies`) rewrite the CLI's `@mcpjam/sdk` range to `^2.1.0` in the same release, so a consumer upgrading the CLI against an old lockfile cannot pair it with an SDK that lacks them. The in-repo range stays `^2.0.0` until then because npm only links the workspace SDK while the range is satisfied by the workspace version.

Behavior fixes in the shared task machinery: the await driver now honors a `Retry-After` recovered from a failed read's error object as the engine's scheduling floor (previously the engine supported it but nothing fed it, and the plain-record header lookup is case-insensitive per RFC 9110); an abort that fires during interactive `input_required` collection settles the drive as `aborted` instead of `input-required`; task `input_required` requests and handler responses are now validated against the canonical spec-type schemas (`ElicitRequest`/`ElicitResult`, `ListRootsRequest`/`ListRootsResult`, `CreateMessageRequest`/`CreateMessageResult`) — the same validation the upstream client applies on the standalone channel — with a new `"malformed-response"` rejection reason, and accepted elicitation answers are additionally self-validated against the request's `requestedSchema` with the same strict dialect-aware rule as standalone MRTR; `setElicitationHandler` no longer requires prior server registration, restoring handler registration before connect.
