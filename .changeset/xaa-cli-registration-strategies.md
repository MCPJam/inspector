`mcpjam xaa run` can now select the client-registration strategy: `--registration <preregistered|dcr|cimd>` (plus `--client-metadata-url` for CIMD). Previously the headless XAA flow was hardcoded to pre-registered even though the shared state machine already implemented all three strategies.

- **SDK**: `XaaFlowConfig` gains optional `registrationStrategy` and `clientIdMetadataUrl`, and `clientId` becomes optional. `runXaaFlow` threads the strategy through the existing state machine and shares ONE internal DCR credential cache across the valid/baseline/probe attempts, so a run performs a single dynamic registration and reuses it. `XaaFlowResult` gains a secret-free `registration` diagnostic (`strategy`, `clientId`, `reused`, `warnings`) — the DCR-minted `client_secret` never enters the result, and registration warnings are retained across attempts (a reused DCR client no longer drops the baseline's warnings). The CIMD metadata-document URL is now configurable (`BaseXAAStateMachineConfig.clientIdMetadataUrl`), defaulting to the hosted XAA document and validated without normalization. `runXaaFlow` enforces its own guards (not CLI-only): a dynamic strategy combined with a pinned `tokenEndpoint` is rejected (it would skip the required metadata discovery). The CIMD document fetch is SSRF-hardened by a new connection-pinned fetch (`fetchPinnedPublicDocument`): it resolves the host once, rejects any private/reserved result against a complete RFC 6890 special-use check (IPv4 + IPv6 + IPv4-mapped), and **pins the validated IP into the connection** so there is no second DNS resolution to rebind — closing the DNS-rebinding window a validate-then-fetch check leaves open. The fetch is HTTPS-only, does not follow redirects, and caps the body at 5 KB (CIMD draft-02 §8.6). The executor opts into it per request via a new `enforcePublicHost` option on `XAARequestExecutor.externalRequest`; loopback RS/token/MCP calls are unaffected.

Semantics are reported honestly: public-client CIMD is flagged as "interoperability passed, security posture not recommended" (ID-JAG draft-04 §9.1 recommends confidential clients), and the CLI warns on stderr that DCR is a RAS diagnostic that simulates the IdP→RAS `client_id` mapping and may leave a registration behind each run (no RFC 7592 cleanup). Confidential CIMD (`private_key_jwt`) and DCR credential cleanup remain follow-ups.
- **CLI**: `--client-id` is required only for `preregistered`; `--client-id`/`--client-secret`/`--token-endpoint-auth-method` are rejected for `dcr`/`cimd` (the identity and auth method are derived). `--token-endpoint` is rejected for dcr/cimd (it skips the AS-metadata discovery those strategies need); `--authz-server-issuer` stays valid. Registration diagnostics — including the public-client CIMD warning — are surfaced in the result and preserved through output redaction.

DCR works end-to-end against a confidential-client RAS. CIMD here is the public-client variant (`token_endpoint_auth_method: none`); a RAS that requires `private_key_jwt` will reject it, so confidential CIMD remains a follow-up.
