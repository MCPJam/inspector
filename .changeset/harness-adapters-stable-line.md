Move the Claude Code and Codex harnesses off the AI SDK canary channel onto the stable `@ai-sdk/harness` 1.0 line

The real-harness engine was pinned to `@ai-sdk/harness@1.0.0-canary.13` with both adapters on `canary.9`. Vercel has since shipped the line as stable, so the inspector now tracks `@ai-sdk/harness@^1.0.96`, `@ai-sdk/harness-claude-code@^1.0.100` and `@ai-sdk/harness-codex@^1.0.98`. The Claude Code CLI inside the sandbox moves from 2.1.146 to 2.1.245 as a consequence.

**Two of the bridge patches are gone, because the adapter now does the work.** MCPJam rewrites the vendored bridge source before shipping it into the sandbox, and every rewrite is a liability that has to be re-verified on each bump. The patch that injected `parent_tool_use_id: null` into the outbound user message is retired — the adapter sets it itself, and re-applying ours would have written the key twice. The patch that wrote `CLAUDE_CODE_EFFORT_LEVEL=unset` into the bridge process is retired too: stable exposes a first-class `env` option, so the value is passed as configuration instead of injected as source. The remaining patches (the assistant-text fallback, and the AI Gateway model overrides) are re-anchored against the new bridge, because the conditions that motivated them are both still present upstream.

The retired `parent_tool_use_id` write is now an assertion rather than a deletion. That key is what stops a subagent's stream from merging into the parent transcript, so if a future adapter drops it the bootstrap fails loudly instead of silently flattening subagent output.

**The model-override patch no longer fights the adapter for the same key.** Claude Code puts its own native model id on the wire and the AI Gateway wants the provider-qualified one, which `settings.modelOverrides` bridges. On the stable line the adapter builds its own `settings` for permission ask-rules and spreads it last, so the previous injection point would have been silently clobbered whenever a run used a non-default permission mode. The overrides are now merged on top of the adapter's own settings at that spread.

**Auth is an environment map now, and the broker model is unchanged.** `HarnessV1Authentication` replaced the structured `{ anthropic } | { openaiCompatible }` options with a flat env map, so `buildBrokerDummyAuth` returns `ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_BASE_URL` and `CODEX_API_KEY`/`OPENAI_BASE_URL` directly. Supplying that map explicitly is also what keeps the adapters from falling back to reading the *server's* own process environment for a model credential, which is the property COMP-23 depends on: the inspector still never holds a real model credential, and the lease is still injected by E2B outside the VM.

**The sandbox-provider contract moved with it.** `bridgePorts` is gone from the provider — port discovery is the adapter's job now, reading the session's `ports` and resolving them through a new required `getPortEndpoint`. `destroy` became required as well, and is implemented as an explicit no-op: MCPJam's computers are owned by the control plane and parked between turns, so a harness-initiated destroy would delete a box we intend to resume. The optional `setRequestTransformations`/`addRequestTransformations` hooks are deliberately left unimplemented, so credential injection stays with the broker rather than moving inside the harness session.

**The pnpm build-script workaround is half retired.** The adapter now ships its own `pnpm-workspace.yaml` pinning the `@anthropic-ai/claude-code` build by exact version, and has dropped the by-hand `install.cjs` rescue it no longer needs. MCPJam stops writing that file — appending a second one would have written the path twice with conflicting content — and keeps it only as a fallback for a future adapter that ships none. The `.npmrc` stays unconditionally: pnpm 10 does not read `allowBuilds` from `pnpm-workspace.yaml`, and the computer template still installs pnpm unpinned.
