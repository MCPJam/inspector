Per-request authorization still applies: a call\nonly succeeds if the key's owner can access that project and server. A key\ncan never reach projects outside its organization.\n\n> [!NOTE]\n>\n> Two deliberate restrictions while in preview:\n>\n> * **API keys cannot manage API keys.** Requests to the key-management surface\n>   with an `sk_…` bearer fail with `403 FORBIDDEN`. Create and revoke keys in\n>   the UI.\n> * **Guest sessions cannot use the API.** Sign in to create keys.\n\n### Keep keys secret\n\nTreat an API key like a password:\n\n* Load it from an environment variable or secret manager — never commit it to\n  source control or ship it in client-side code.\n* Scope keys narrowly: one key per integration, named so you can tell them apart.\n* Rotate by creating a replacement key, switching traffic, then revoking the old one.\n* If a key leaks, revoke it immediately in\n  [**Settings → API keys**](https://app.mcpjam.com/settings/api-keys).\n\nIf you see `401 UNAUTHORIZED` with `details.reason: \"ORPHANED_KEY\"`, the key\nis no longer bound to an organization and cannot be used — create a new key\nfrom [Settings](https://app.mcpjam.com/settings/api-keys).\n\n## Conventions\n\n**Requests.** Operations on servers are `POST` with a JSON body (most accept\nan empty `{}`). **Reads** — the catalog listings and eval-run polling — are\n`GET` and take their options (`cursor`, `limit`, filters) as query\nparameters.\n\n**Responses.** Three envelope shapes, used consistently:\n\n| Kind | Shape |\n| - | - |\n| Single resource | The resource object directly |\n| Collection | `{ \"items\": [...], \"nextCursor\": \"...\" }` — `nextCursor` omitted on the last page |\n| Error | `{ \"code\": \"...\", \"message\": \"...\", \"details\": {...} }` with a matching HTTP status |\n\n**Pagination.** Collections are cursor-based. Pass the previous response's\n`nextCursor` as `cursor` in the next request (body field on `POST` lists,\nquery parameter on `GET` lists). Cursors are opaque — don't parse them.\n\n**Authoring vs running suites.** `POST /eval-suites` creates a runnable suite\n(the suite plus its test cases) **synchronously** and responds `201` with the\n`suiteId`, WITHOUT running anything — author once, run later. `POST /eval-runs`\nis the async counterpart: it validates and creates a run synchronously, then\ndetaches execution and responds `202` with a `runId`. Poll\n`GET /eval-runs/{runId}` until `status` is `completed`, `failed`,\n`cancelled`, or `timed_out`.\n\n**IDs.** Every identifier the API takes is discoverable through the API\nitself: `GET /projects` lists your projects, `GET /projects/{projectId}/servers`\nlists each project's servers, and `GET /projects/{projectId}/eval-suites`\nlists its eval suites. Start from `GET /me` to confirm which account a key\nacts as.\n\n## Errors\n\nErrors always use the canonical body `{ code, message, details? }`. The `code`\nis stable and machine-readable; `message` is human-readable and may change;\n`details` is an optional, unstructured bag.\n\n| Code | HTTP | Meaning |\n| - | - | - |\n| `UNAUTHORIZED` | 401 | Missing, invalid, revoked, or orphaned key |\n| `OAUTH_REQUIRED` | 401 | The **target MCP server** needs an OAuth grant — distinct from a bad key |\n| `AUTH_REQUIRED` | 403 | The **target MCP server** allowed the connection and asked for sign-in on this call. `details.authChallenge` carries the parsed challenge. Your key is fine — see [Sign-in challenges](#sign-in-challenges) |\n| `FORBIDDEN` | 403 | Key is valid but not allowed to do this — or the **target MCP server** rejected the credentials MCPJam presented (retrying with a different MCPJam key will not help; reconnect or re-authorize the server) |\n| `VALIDATION_ERROR` | 400 | Malformed body or parameters |\n| `NOT_FOUND` | 404 | Unknown project, server, or resource |\n| `CONFLICT` | 409 | The resource isn't in a state that accepts this write — a stale `expectedRevision`, a duplicate name, or an environment that can't currently be launched. Re-read and retry |\n| `FEATURE_NOT_SUPPORTED` | 422 | The target server doesn't support this MCP capability |\n| `RATE_LIMITED` | 429 | Too many requests — see [Rate limits](#rate-limits) |\n| `SERVER_UNREACHABLE` | 502 | Could not connect to the target MCP server |\n| `TIMEOUT` | 504 | The target MCP server connected but didn't respond in time |\n| `INTERNAL_ERROR` | 500 | Something failed on our side |\n\nNew error codes may be **added** over time; treat unknown codes as\nnon-retryable failures unless the HTTP status says otherwise.\n\n### Sign-in challenges\n\nSome MCP servers allow the connection and ask for sign-in only on a protected\ncall. The API never starts a sign-in. It reports the challenge instead:\n\n* **HTTP 401 from the MCP server** on `tools/call`: the API answers\n  `403 AUTH_REQUIRED`. `details.authChallenge` carries the parsed challenge:\n  its `source` (`http_401`), and the `error`, `requiredScope`, and\n  `resourceMetadataUrl` the server sent, when present.\n* **An `isError` result carrying `_meta[\"mcp/www_authenticate\"]`** (the\n  ChatGPT convention): the call succeeds, and the `CallToolResult` is returned\n  unchanged with an additive `authChallenge` field (`source:\n  \"tool_result_meta\"`). A field the server already set under that name is never\n  overwritten.\n\n`AUTH_REQUIRED` is not `UNAUTHORIZED`: your MCPJam key is fine, so a different\nkey will not help. Complete the OAuth flow for that server yourself, upload the\ntoken to one of its [accounts](#server-accounts), and call again. See\n[Mid-session sign-in](https://docs.mcpjam.com/inspector/lazy-authentication.md).\n\n## Rate limits\n\nEach key gets **60 requests per minute** sustained, with bursts up to **10**.\nExceeding it returns `429 RATE_LIMITED` with a `Retry-After` header (in\nseconds):\n\n```http theme={\"theme\":\"css-variables\"}\nHTTP/1.1 429 Too Many Requests\nRetry-After: 7\n\n{ \"code\": \"RATE_LIMITED\", \"message\": \"API key rate limit exceeded. Slow down and retry.\" }\n```\n\nHonor `Retry-After`, add jittered exponential backoff, and expect these limits\nto be tuned during the preview.\n\nOther `429`s — the per-minute brakes and daily budgets described with the\nendpoints below — carry `Retry-After` whenever the refusal knows when it\nlifts, which is the ordinary case. Treat it as a hint that is usually there\nrather than a guarantee: a refusal that reaches you without one still needs\nyour backoff, so **never** block waiting for a header that may not come.\n\n## Endpoints\n\nEach endpoint is fully documented — request and response schemas, examples,\nand an interactive playground — under **Endpoints** in the sidebar.\n\n**Catalog** — discover the IDs everything else takes:\n\n| Endpoint | What it does |\n| - | - |\n| `GET /me` | The account behind the key |\n| `GET /organizations` | The organizations the caller belongs to — where `organizationId` comes from. Read these in cost order: metrics, usage and signals are\ndeterministic and free; the insights request runs a model.\n\n| Endpoint | What it does |\n| - | - |\n| `GET .../studies/{studyId}/metrics` | Volumes, completion and feedback rates. `?population=real\\|synthetic` splits real visitors from swarm runs |\n| `GET .../studies/{studyId}/usage` | Which models, tools and servers the sessions used. **Check `scan.truncated`** before quoting a rate |\n| `GET .../studies/{studyId}/signals` | What the miner found in the current window — and where you get the `windowId` |\n| `GET .../studies/{studyId}/findings` | Every finding raised over this study, dismissed ones included |\n| `GET .../studies/{studyId}/windows/{windowId}/insights` | One window's insights. **`404` means nobody asked**, which is not the same as `pending` |\n| `POST .../studies/{studyId}/insights` | **No credits; counts against `insightsPerDay`.** `202` with the `windowId` to poll. `409` if the window has not been mined yet |\n| `DELETE .../studies/{studyId}/insights` | Release a generation stuck `pending`. Failure/skip reasons and `deferredUntil` explain incomplete work;\n`awaitingTaxonomy`, `unassigned`, and `staleAssignments` distinguish catalog\ncoverage from extraction. `projectionPending` and `projectionFailed` describe\nthe map independently. Reading this response never starts analysis.\n\nTaxonomy entries carry the published version and discovery status. Theme ids\nremain stable across additions and cosmetic renames. An older assignment\nversion can still be valid when its theme is unchanged; a retired or replaced\nmembership remains visible while cached reassignment completes. These are\ncurrent views with version provenance, not historical traffic snapshots.\n\nCheck `scan.truncated` and `analysis.sampled` before interpreting coverage as a\nwhole-scope total. Map reads separately expose displayed counts, scope totals,\nsampling, and freshness; a swarm run's displayed counts cover only its requested\ngoal runs. A pending projection contributes to the unmapped count rather\nthan a fabricated map node.\n\nThe five analytics shapes above are documented as **open objects** on purpose.\nTheir upstream projections grow with the product and the SDK types them the\nsame way, so pinning a field list would turn every new metric into a spec\nviolation. Read what you recognize; ignore the rest.\n\n> [!WARNING]\n>\n> Requesting insights consumes **no credits** — the model cost is on MCPJam.\n> It still draws on the same `insightsPerDay` ledger as eval-run and swarm run\n> insights — one REQUEST quota, three producers. Poll the window read rather\n> than re-requesting; `force: true` deliberately takes a second slice, which is\n> why it is never inferred from anything else.\n\n**Feedback** — report a problem with MCPJam itself to the MCPJam team:\n\n| Endpoint | What it does |\n| - | - |\n| `POST /feedback` | Send a bug report, missing-capability note, or other feedback to the MCPJam team. Accepts `Idempotency-Key` (validated strictly — an empty or over-long key is `400`, not silently ignored; the same key with different content is `409`). **The text goes to the MCPJam team, outside your organization, and is kept for 180 days.** |\n\n> [!NOTE]\n>\n> `POST /feedback` is the same endpoint the `send_feedback` MCP tool calls.\n> Include the failing call's `x-request-id` as `requestId` when you have one —\n> it lets the team find that request in the server logs. An identical report\n> from you in the last 24 hours returns `duplicate: true` with the original\n> receipt instead of filing a second report.\n\n**Planning** — one read that answers \"may I?\" before you try:\n\n| Endpoint | What it does |\n| - | - |\n| `GET .../projects/{projectId}/capabilities` | The caller's role, the beta gate's state, plan limits, and the booleans to branch on |\n\n> [!NOTE]\n>\n> `capabilities` is a **planning aid, not a gate**. Every write still enforces\n> independently, so a `true` here that races a flag flip costs you a clean\n> `403` rather than an incorrect success — and nothing should consult it\n> *instead of* trying. It exists because agent surfaces are static: an MCP tool\n> catalog is built with no organization in hand, so the alternative is\n> attempting the write and reading the failure, by which point the agent has\n> usually already told someone what it was about to do.\n\nThe same surface is available as an [OpenAPI\nspecification](https://raw.githubusercontent.com/MCPJam/inspector/main/docs/reference/openapi.json)\nfor Postman, Swagger UI, or client generation.\n\n## Server accounts\n\nA saved server signs in with one or more **accounts**. When your test users\ncan't use the browser sign-in, for example because a password and a passkey\nare required every day, your CI can sign in itself and upload the fresh token\nto a named account before each run.\n\n| Endpoint (`/projects/{projectId}/servers/{serverId}/...`) | What it does |\n| - | - |\n| `GET .../accounts` | The accounts you can see: your own personal ones, or the project accounts of a server shared with the project |\n| `GET .../accounts/{account}` | One account |\n| `PUT .../accounts/{account}` | Upload a token. Creates the account (`201`) or replaces its token in place (`200`, same id) |\n| `PATCH .../accounts/{account}` | Rename it (`name`), make it the default (`isDefault: true`), or both |\n| `DELETE .../accounts/{account}` | Delete it, and ask the token's issuer to revoke the token |\n\n```bash theme={\"theme\":\"css-variables\"}\ncurl -fsS -X PUT \\\n  \"https://app.mcpjam.com/api/v1/projects/$PROJECT_ID/servers/$SERVER_ID/accounts/test-automation-1\" \\\n  -H \"Authorization: Bearer $MCPJAM_API_KEY\" \\\n  -H \"Content-Type: application/json\" \\\n  -d '{\n    \"tokens\": { \"sensitive_value\": \"[REDACTED]\"$ACCESS_TOKEN\"'\", \"expires_in\": 3600 },\n    \"clientInformation\": { \"clientId\": \"'\"$CLIENT_ID\"'\" }\n  }'\n```\n\nEvery answer is the account: its `id`, `name`, `kind`, `isDefault`,\n`needsReconnect`, `hostedOnly`, `expiresAt`, `createdAt` and `updatedAt`. No\nroute returns a token, and none can.\n\n### Addressing an account\n\n`{account}` is an account id or a name. A well-formed account id is always\nread as an id: it matches that account or answers `404`, and an upload to an\nunknown id never creates one. Anything else is a name, matched ignoring case.\nA name no account has makes `PUT` create the account; on every other route it\nanswers `404`. A name two accounts share answers `409` with both ids in\n`details.accountIds`.\n\nA name is letters, digits, `.`, `_` and `-`, starts with a letter or digit, and\nis at most 64 characters. One outside that rule, or one that is also a\nwell-formed account id, is refused with `400`, never cleaned up. Names are\nunique on the server, ignoring case.\n\n### What an upload stores\n\n* **Nothing checks who a token belongs to.** A name is your own label, and\n  replacing a token replaces it whoever the token belongs to. Keep each name\n  for one test user.\n* **Uploaded accounts are hosted-only.** Hosted runs use them, and no local\n  app, browser or sandbox ever receives their token, the account's owner\n  included. Asking for it is refused with a message naming the rule.\n* **The token is bound to the server URL saved in the project.** The body\n  takes only `tokens` and `clientInformation`. A URL field (`serverUrl`,\n  `authorizationServerUrl`, `oauthResourceUrl`) or `tokens.id_token` is\n  refused with `400`, as is any field the route doesn't know.\n* **Each token field is at most 16 KB.**\n* **A refresh token is optional, and usually best left out.** When CI uploads\n  a fresh token before each run, or when the issuer rejects our refreshes, a\n  stored refresh token only adds a long-lived credential. Without one, an\n  expired account lists `needsReconnect: true` and keeps its id until the next\n  upload restores it.\n* **Uploads are budgeted** per person and server: 60, refilling at 120 an\n  hour. Past it the answer is `429` with `Retry-After`.\n\n### Who can upload\n\nAn API key acts as the person who created it, with all of that person's\naccess. For personal accounts, upload with the key of a dedicated member who\nis not a project admin, so a leaked CI key can't do an admin's work. On a\nserver shared with the project, accounts are project accounts: only a project\nadmin can upload, rename or delete them, and every member's hosted runs can\nuse them.\n\n### Running evals as an account\n\nA run with no saved account choice acts as the server's **default** account.\nTo run evals from CI as one account, upload its token, make it the default,\nthen start the run:\n\n```bash theme={\"theme\":\"css-variables\"}\ncurl -fsS -X PATCH \\\n  \"https://app.mcpjam.com/api/v1/projects/$PROJECT_ID/servers/$SERVER_ID/accounts/test-automation-1\" \\\n  -H \"Authorization: Bearer $MCPJAM_API_KEY\" \\\n  -H \"Content-Type: application/json\" \\\n  -d '{ \"isDefault\": true }'\n```\n\nThe CLI takes the same steps with `mcpjam cloud server-accounts set`, which\nreads the token from a file, an environment variable or stdin, and\n`mcpjam cloud server-accounts default`. See the\n[CLI reference](https://docs.mcpjam.com/cli/reference.md#cloud-server-accounts-commands).\n\nThe default is shared by every run that key starts, so don't run the same\nkey's runs at the same time with different defaults. Where your organization\nhas account choice for eval suites, a suite can instead save the accounts it\nruns as, in its settings in the app; a run with a saved choice uses those\naccounts and ignores the default.\n\n### Deleting an account\n\n`DELETE` removes the account and its stored token, and asks the token's issuer\nto revoke the token where the issuer supports revocation. That is best effort,\nand it also ends any copy of the same token you still hold. The default\naccount can't be deleted while other accounts exist (`409`): make another\naccount the default first.\n\n### The deprecated import route\n\n`POST .../oauth/import-tokens` still works, and is removed 90 days after the\naccounts API shipped. It uploads to your default account, creating an unnamed\none when the server has none, and keeps its old body and its old\n`{ imported, expiresAt }` answer. Every answer carries `Deprecation: true`, a\n`Sunset` date and a `Link` to `.../accounts`.\n\nAn account this route creates is hosted-only. An existing default it writes\ninto keeps whatever rule it had. Its `serverUrl` must be the URL saved in the\nproject, or the answer is `400`. `authorizationServerUrl`, `oauthResourceUrl`\nand `tokens.id_token` are accepted and ignored. Move to\n`PUT .../accounts/{account}`, which names the account it writes.\n\nThe error codes these routes add to `details.code` are listed in the\n[error code reference](https://docs.mcpjam.com/troubleshooting/error-codes.md#server-account-errors).\n\n## Run evals from the API\n\nThe shortest useful loop — create a run with one inline test, then poll:\n\n```bash theme={\"theme\":\"css-variables\"}\n# 1. Create (responds 202 immediately; -f + jq -e fail fast on errors)\nRUN_ID=$(curl -fsS -X POST \\\n  \"https://app.mcpjam.com/api/v1/projects/$PROJECT_ID/eval-runs\" \\\n  -H \"Authorization: Bearer $MCPJAM_API_KEY\" \\\n  -H \"Content-Type: application/json\" \\\n  -d '{\n    \"suiteName\": \"smoke\",\n    \"serverIds\": [\"'$SERVER_ID'\"],\n    \"tests\": [{\n      \"title\": \"echo works\",\n      \"runs\": 1,\n      \"model\": \"anthropic/claude-haiku-4.5\",\n      \"provider\": \"anthropic\",\n      \"steps\": [\n        { \"id\": \"s1\", \"kind\": \"prompt\", \"prompt\": \"Use the echo tool to say hi\" },\n        {\n          \"id\": \"s2\",\n          \"kind\": \"assert\",\n          \"assertion\": {\n            \"type\": \"toolCalledWith\",\n            \"toolName\": \"echo\",\n            \"args\": { \"args\": { \"text\": \"hi\" } }\n          }\n        }\n      ]\n    }]\n  }' | jq -er .runId)\n\n# 2. Poll until status is completed | failed | cancelled | timed_out\ncurl -s \"https://app.mcpjam.com/api/v1/projects/$PROJECT_ID/eval-runs/$RUN_ID\" \\\n  -H \"Authorization: Bearer $MCPJAM_API_KEY\"\n\n# 3. If it did not pass, read the decision summary FIRST\ncurl -s \"https://app.mcpjam.com/api/v1/projects/$PROJECT_ID/eval-runs/$RUN_ID/decision-summary\" \\\n  -H \"Authorization: Bearer $MCPJAM_API_KEY\"\n\n# 4. Or go straight to per-iteration tool calls, token usage, latency\ncurl -s \"https://app.mcpjam.com/api/v1/projects/$PROJECT_ID/eval-runs/$RUN_ID/iterations\" \\\n  -H \"Authorization: Bearer $MCPJAM_API_KEY\"\n```\n\nThe decision summary composes steps 2 and 4 into one versioned object so every\nclient reads a run the same way. Four things to know before gating on it:\n\n* **`measurementUnit` ships with every count.** Under per-case grading the\n  counts are case-execution *variants*, with iterations as trials inside them;\n  under a suite-wide accuracy threshold they are trials. The same suite reports\n  a different total under each — 3 against 15 for three cases run five times —\n  so a count without its unit is not a fact, and a rate is never converted\n  across that line.\n* **It explains the verdict; it never re-decides it.** The run's own decision is\n  the authority and is carried through on `decision`. The per-trial\n  `diagnostics` sit underneath it — a case can pass with a failing trial in it,\n  so tallying diagnostics gives a different answer than the platform reached.\n* **`verdict: \"notEstablished\"` is not a failure and not `inconclusive`.** It\n  means no verdict exists at all (unfinished, stopped early, or undecidable);\n  `undecided.reason` says which. `inconclusive` *is* a decision — the validity\n  phase ran and withheld a verdict.\n* **`diagnostics.complete` says whether you have the whole list.** A page\n  fetched with a `cursor` is never complete, and `scannedIterations` separates\n  \"nothing failed\" from \"we did not look\".\n\nEvidence is scoped to the claim it supports: for a measured failure the span\nids, prompt indexes and reasons come from the first failed stage's row alone,\nand `evidence.tracePath` is an API-relative path you can append to your base URL\nto read the full trace.\n\n`model` takes an id from the hosted catalog — `provider/name` form, e.g.\n`anthropic/claude-haiku-4.5` — and runs on your organization's credits.\nProvider-native ids (e.g. `claude-sonnet-4-5`) are bring-your-own-key: pass\nthe key in `modelApiKeys`. A model the API can't execute is rejected at\ncreate time with `VALIDATION_ERROR`; `details.hostedModels` lists the valid\nhosted ids for that provider.\n\nReruns are even shorter: `{ \"suiteId\": \"...\" }` reruns the suite exactly as\nconfigured, connecting the suite's saved server selection (the `202` response\nlists the resolved `servers`). Pass `serverIds` to override the selection; a\nsuite with no saved selection requires it (`VALIDATION_ERROR` with\n`details.reason: \"NO_SAVED_SERVER_SELECTION\"` otherwise).\n\n### Running against a project environment\n\nA [project environment](#endpoints) is launchable only through a suite that has\nit **attached**. Attach them first with\n`PATCH /projects/{projectId}/eval-suites/{suiteId}` and an `environmentIds`\narray (send `null` to detach them all; `[]` is rejected — use `null`), then\npass `environmentId` on the run. It must be one of that suite's attached\nenvironments; anything else is a `400` with\n`details.reason: \"ENVIRONMENT_NOT_ATTACHED\"`, raised before any case is\nauthored or any server connected.\n\nOmitting `environmentId` is meaningful, and depends on the suite:\n\n* **no** attached environments → the run uses the saved server selection, as before;\n* **exactly one** attached → that environment is used automatically. The `202`\n  response's `environment` field says so;\n* **several** attached → `400` with `details.reason: \"ENVIRONMENT_REQUIRED\"`,\n  naming the candidates.\n\nThe environment supplies the closed server set — including the servers its\npinned plugin versions contribute — so `serverIds` is not required and is\n**rejected** alongside it (`400`), rather than accepted and ignored: honoring\nboth would connect a different set than the run is stamped with. The same goes\nfor a `serverIds` override on an environment-based suite\n(`details.reason: \"ENVIRONMENT_SERVERS_NOT_OVERRIDABLE\"`).\n\nThe run is pinned to the environment revision resolved at launch: if the\nenvironment changes in between, the run is rejected with `CONFLICT` (409)\nrather than executing against a different configuration than the one whose\ntools were captured. Use\n`GET /projects/{projectId}/environments/{environmentId}/resolve` to see what it\nwill connect before launching.\n\nWhen creating a new inline suite, `POST .../eval-runs` also accepts `hosts: [{ host: \"Claude\", servers: [\"my-server\"] }]`, using the same host name or ID and optional server selection as `POST .../eval-suites`. A single host is selected for the run automatically. With multiple attachments, use `namedHostId` to select the run's client. For an existing suite, update its attachments first. If `hosts` is omitted, the backend supplies the project's default client.\n\nRun reads and listings expose `client: { id, name, source, hostStyle?, modelId? }` when recorded. `id` is the named host ID or `null`; `source` is `environment`, `attached_host`, `suite_default`, or `sdk`. The name is durable even if the host is deleted. SDK executions use `SDK harness`; `launcher.client` separately identifies the launching process. Older runs without a descriptor omit `client`. `modelSource: \"case\"` means the run's sole model came from its case snapshot; `client_default` and `override` retain their existing meanings.\n\nEvery run records which environment it used. `GET .../eval-runs/{runId}` (and\nthe run listings) return `environment: { id, name, revision }` — read from the\nrun's immutable snapshot, not the suite's current attachments — or `null` for a\nrun that used a saved server selection.\n\nPer-organization\nconcurrency is capped (default **2** concurrent runs); exceeding it returns\n`429` with `details.reason: \"CONCURRENT_RUN_LIMIT\"` — wait for an active run\nto finish.\n\nIf a server answers `401 OAUTH_REQUIRED`, complete the OAuth flow yourself\n(the SDK's `runOAuthLogin` handles interactive, headless, and\nclient-credentials flows) and upload the token to one of the server's\n[accounts](#server-accounts). Subsequent runs inject the stored token, and\nrefresh it server-side when you stored a refresh token.\n\n## Reasoning effort\n\nA reasoning effort is a **saved setting on a model selection**, not a free-standing\nfield. A `ModelSelection` (`modelId`, `source`, an optional `connectionRef`, and a\n`fallback`) carries it as `settings.reasoningEffort`, and the same shape is\naccepted everywhere a model choice is saved:\n\n| Where | Field |\n| - | - |\n| Client (`PATCH /projects/{projectId}/clients/{client}`) | `set.modelSelection` (or `config.modelSelection` on a whole-config replacement) |\n| Project environment (`POST`, `PATCH`, `POST .../ensure-adhoc`) | `modelSelection`, read back on the environment |\n| Eval case (`POST`, `PATCH .../cases`) | `models[].selection`, read back on the case |\n| Eval suite (`PATCH /projects/{projectId}/eval-suites/{suiteId}`) | `executionConfig.modelSelection`, read back on the suite |\n\n```json theme={\"theme\":\"css-variables\"}\n{\n  \"modelId\": \"openai/gpt-5\",\n  \"source\": \"hosted\",\n  \"settings\": { \"reasoningEffort\": \"high\" },\n  \"fallback\": { \"provider\": \"none\", \"model\": \"none\" }\n}\n```\n\n* **Levels.** `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`. Which of\n  them a model accepts is `supportedReasoningEfforts` on each row of the public\n  `GET /v1/models` catalog. An empty or absent list means no effort is offered for\n  that model — do not guess one.\n* **Applied or refused, never dropped.** A saved effort is applied by the route\n  the run takes and recorded on the execution record, or refused with\n  `capability_missing` before any spend. An effort replaces the sampling\n  temperature.\n* **A selection belongs to one model.** It must be for the `model` / `modelId` it\n  sits beside (`400` otherwise); sent alone it pins its own model. A bare model\n  change on a suite or environment drops a selection saved for the old model\n  instead of failing.\n* **Cases keep their selections.** A `models` PATCH replaces the array, but an\n  entry that omits `selection` keeps the case's existing selection for that\n  model. Send `selection: null` to drop it.\n* **Clearing.** `null` clears a saved selection on a client `set`, an environment\n  or a suite, keeping the bare model id.\n* **Never a secret.** A selection has no credential field; an unknown key\n  (`apiKey`, …) is a `400`.\n* **Environments need the capability.** `GET .../environments/capabilities`\n  reports `modelSelections`; an older deployment rejects the field.\n* **`advancedConfig.reasoningEffort` is retired.** It was never applied, so\n  writing it is a `400` pointing at `models[].selection.settings`, and a stored\n  value is refused by the runner.\n\n`POST /chat-sessions/messages` takes a top-level `reasoningEffort` for a\nper-request effort. Like `temperature`, it is pinned on the session's **first\nturn** (a continuation that restates it is refused), it wins over the effort a\n`hostId`'s saved selection carries, and it cannot be combined with `temperature`.\n\nThe SDK, CLI, MCP tools and in-app agent all go through the same operations:\n`--effort` / `reasoningEffort` is a shorthand that edits the selection the target\nalready has, and is refused (`send modelSelection`) when there is none.\n\n## Not in the API yet\n\nTo set expectations while in preview, these are **not** available over the API\ntoday (most exist in the hosted inspector UI):\n\n* Creating or revoking API keys (UI-only by design — see [Authentication](#authentication))\n* Chat and conformance suites\n* Browser-based OAuth flows initiated by the API (complete OAuth yourself,\n  then upload the token to one of the server's [accounts](#server-accounts))\n\nIf one of these blocks you, tell us on\n[Discord](https://discord.gg/JEnDtz8X6z) — it directly shapes what we\nstabilize first.\n\n## Versioning & stability\n\n* The API is **path-versioned** (`/api/v1`). When it reaches general\n  availability, breaking changes will require a new version path.\n* **During the preview**, breaking changes to v1 may still happen; we'll note\n  them in the [changelog](https://docs.mcpjam.com/changelog/overview.md).\n* **Additive changes** — new endpoints, new optional request fields, new\n  response fields, new error codes — are considered non-breaking and can ship\n  at any time. Write clients that ignore unknown fields.\n* Error **codes** are stable identifiers; error **messages** are not.\n\n### Renamed surfaces\n\nThree nouns this API used are now what the product calls them: `scenario` is\n**study**, `journey` is **goal**, and `wave` is **swarm run**. The paths, the\noperation names, the SDK types and the noun-bearing response fields all moved:\n\n| Was | Is |\n| - | - |\n| `/projects/{projectId}/scenarios[/{scenarioId}]` | `/projects/{projectId}/studies[/{studyId}]` |\n| `/projects/{projectId}/user-testing/scenarios/{scenarioId}/…` | `/projects/{projectId}/studies/{studyId}/…` |\n| `/projects/{projectId}/environments/{environmentId}/scenario` | `.../environments/{environmentId}/study` |\n| `/projects/{projectId}/journeys[/{journeyId}]` | `/projects/{projectId}/goals[/{goalId}]` |\n| `/projects/{projectId}/journey-runs/{runId}` | `/projects/{projectId}/goal-runs/{runId}` |\n| `/projects/{projectId}/journeys-overview`, `.../journey-findings` | `.../goals-overview`, `.../goal-findings` |\n| `/projects/{projectId}/waves/{waveId}/insights` | `/projects/{projectId}/swarm-runs/{swarmRunId}/insights` |\n\nResponse fields followed their nouns: `scenarioId` → `studyId`, `journeyId` →\n`goalId`, `waveId` → `swarmRunId`, and `sessionsPerTarget` → `iterations`.\n\nTwo reads became one: `get_scenario` served the execution settings and\n`get_user_testing_scenario` served the environment id and the insights\nenvelope. `get_study` returns both, and the two caller-dependent fields are\nabsent rather than null when you may not have them.\n\n**Every old path still works** and is unchanged, including its old response\nspellings. Each one answers with `Deprecation: true` and a `Link` header naming\nits successor. They are undocumented on purpose — the spec is what a new\nintegration reads — and they are removed at general availability.\n\nA handful of operations kept their names through the rename and so have no\ndeprecated twin to hold the old field spellings. `get_swarms_overview`,\n`create_swarm` and `update_swarm` emit both and accept either — never both in\none request — until general availability.\n\n### Vocabulary\n\nA name can move behind an alias; a VALUE cannot. `sourceType` is one field with\none string in it, and a client switching on `\"scenario\"` has no second name to\nfall back to. So the values negotiate.\n\nSend `x-mcpjam-api-vocabulary: 2` and the renamed values read canonically:\n\n| Field | Vocabulary 1 | Vocabulary 2 |\n| - | - | - |\n| session `sourceType` | `scenario` | `study` |\n| session `parentRef.kind` | `scenario`, `journeyRun` | `study`, `goalRun` |\n| session `parentRef` ids | `scenarioId`, `journeyRunId`, `journeyRefId` | `studyId`, `goalRunId`, `goalRefId` |\n| share `resourceType` (field AND path segment) | `scenario` | `study` |\n| trace-destination `sourceTypes` | `scenario` | `study` |\n\nAbsent means `1`, which is byte-for-byte today's contract. Any other value is a\n`400`. On the way IN, a vocabulary-2 request may name a filter or a path segment\nby either spelling; a vocabulary-1 request may use only the legacy one, because\na boundary that accepts a spelling it does not announce is one two\nimplementations can disagree about.
