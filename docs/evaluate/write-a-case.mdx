A case is one scenario you want to verify: what the user asks, which tool should handle it, and the assertions that grade the result. Each time the case runs counts as one iteration.

## Add a case

<Steps>
  <Step title="Open the suite">
    In the Evaluate tab, open **Suites** and pick a suite.
  </Step>
  <Step title="Start a blank case">
    On the **Test Cases** card, click **Add case**, then **Add manually**. A suite with no cases shows "No cases yet" instead; click **Describe** there. It opens the same case form beside a chat, and you can fill the form in yourself.
  </Step>
  <Step title="Write the prompt">
    Type what the user asks in the first **User prompt**.
  </Step>
  <Step title="Add what to check">
    Click **Add assertion or action** and pick from the list. The sections below explain the choices.
  </Step>
  <Step title="Save and run">
    Click **Save**, then **Run**.
  </Step>
</Steps>

A new case is a draft until you save it. Leaving without saving adds nothing to the suite, and **Run** stays disabled on an unsaved draft.

## Actions and assertions

**Add assertion or action** opens one list with two kinds of entry. Actions add a step to the run:

| Action | What it adds |
| --- | --- |
| **User prompt** | Another user message. A second prompt makes the case multi-turn. |
| **Interact** | A step that acts on a rendered MCP App view. |
| **Call tool** | A tool call on a named server with arguments you set, made without the model. |

Assertions grade the run. Each entry in the list says where it applies:

- **After this action**: graded at that point in the run, over the turn it sits in. Tool-selection and response assertions, such as "Tool was called with…" and "Response contains…", work this way.
- **After the run**: graded once over the finished transcript, and listed under "After run checks". "Token budget under N", "Fewer than N user turns" and the tool-result assertions work this way.

The assertion's kind decides which of the two it is. Some kinds are marked "Advisory only" in the list. See [Assertions](/evaluate/reference/assertions) for every kind and its fields.

## Which tool should handle it?

The route is the case's answer to "Which tool should handle it?". There are three answers, and a named tool comes in two strictness levels. Set each from **Add assertion or action**:

| Answer | How to set it | Passes when |
| --- | --- | --- |
| A named tool: reach it | Add "Tool was called with…" under the prompt, then pick the tool and its arguments. | The model calls that tool with matching arguments. Other calls, in any order, are allowed. |
| A named tool: exact route | Also add "Tools must be called in this exact order". | The calls happen in the listed order, with no extra calls. |
| No tool should be called | Add "No tools should be called". | The model calls no tool. This makes the case negative. |
| Any route | Add no "Tool was called with…", but add another assertion or an **Expected outcome**. | Every assertion passes. The route itself is not graded. |

When you inspect a past iteration, its route row names the answer that was in effect, such as "Reach read_note", "Exact route: read_note → update_note", **No tool should be called**, or "Any route — graded by the evaluators below". On a read-only case, such as one managed in code, **Matching options** shows which strictness the route uses: **Reach the tool** or **Exact route**.

A new case with no tool assertion, no other assertion and no expected outcome would pass without checking anything. **Save** stays disabled with "Choose which tool should handle it, or that no tool should be called."

### Argument values

Arguments compare under the suite's argument matching. In the default partial mode, an expected value of `"string"`, `"number"`, `"boolean"`, `"object"`, `"array"`, `"null"` or `"any"` matches any value of that type, so you can check the shape of a call without pinning a literal:

```json
{ "query": "string", "limit": "number" }
```

## Negative cases

A negative case is one whose route says **No tool should be called**. It passes only if the model answers without calling a tool. Good negative cases are prompts a careless model would turn into a tool call:

| Prompt | Why no tool should fire |
| --- | --- |
| "What parameters does `search` take?" | A question about the tool, answerable from its description. |
| "Thanks, that's all I needed." | A thank-you with nothing to do. |
| "Delete it." (with nothing selected earlier) | Ambiguous; the model should ask which item. |

A case that names no tool is not negative. It is an "Any route" case, graded by its other assertions. If a negative case also carries an assertion that requires a tool call, from the case or from the suite, the editor flags the conflict: "This check conflicts with another check that requires a tool call."

## Multi-turn cases

Add a second **User prompt** from **Add assertion or action** at the end of the first turn. The run plays both prompts as one conversation.

An assertion placed under a prompt sees only that prompt's turn: its tool calls, its final message and its tool errors. A "Tool was called with…" under the second prompt passes only if the call happens in the second turn. "No tool errors" placed under a prompt is labelled "No tool errors so far", because it sees only what has happened by that point. Put an assertion after the run when it should cover the whole conversation.

Removing a prompt that has assertions under it asks first, because those assertions would move under the previous step and grade that turn instead.

## Required and Advisory

Every assertion has a role, shown on its row:

| Role | What a miss does |
| --- | --- |
| Required | The iteration fails. |
| Advisory | The miss is shown on the result. The iteration does not fail. |

Assertions are Required unless set otherwise. When your workspace supports editing roles, open an assertion's row to change it.

A Required assertion under a prompt stops the run when it fails. The steps after it do not run, and the result marks them Skipped. An Advisory miss never stops the run.

## Expected outcome

**Expected outcome** holds one goal sentence for the whole case. The goal completion judge grades the finished run against the first of these that exists:

1. The goal sentence you write here. Suite criteria also apply.
2. The case's route: the tools it expects, or that no tool should be called.
3. The suite's grading criteria.
4. The user's request itself. With nothing else to grade against, the judge caps the score at 0.85.

Turn on **Skip the judge for this case** to stop the judge grading this case. The switch appears when the suite's judge is not off. See [Configure grading](/evaluate/configure-grading) for the judge's model, threshold and role.

## Invalid JSON

Fields that take JSON, such as tool arguments and result schemas, are checked as you type. While any of them holds invalid JSON, the field is highlighted, and **Save** and **Run** are disabled with a tooltip asking you to complete the highlighted fields. Fix the JSON to enable them again.

## Inspect a past iteration

<Steps>
  <Step title="Open History">
    In the case editor, click **History** to list the case's past iterations.
  </Step>
  <Step title="Pick one">
    The form switches to the case as it was when that iteration ran, read-only. A banner reads "Viewing run · Iteration #N".
  </Step>
  <Step title="Compare with your draft">
    If the case has changed since, the banner shows **Changed**.
  </Step>
  <Step title="Return to editing">
    Click **Edit case** to go back to the current draft.
  </Step>
</Steps>

## The same case in a suite file

A case written in the app has the same shape as one in a suite file run by `mcpjam test`: a list of steps, each a `prompt` or an `assert`. This case asks two questions in one conversation and checks each turn.

<Tabs>
  <Tab title="Inspector">
    1. First **User prompt**: "What does note 7 say?"
    2. Under it, add "Tool was called at least once" with the tool `read_note`.
    3. Add a second **User prompt**: "Thanks, that's all."
    4. Under it, add "Tool was never called" with the tool `delete_note`.
  </Tab>
  <Tab title="Suite file">
    ```yaml
    cases:
      - id: c_read_then_thanks
        title: reads a note, then does nothing on thanks
        steps:
          - id: s1
            kind: prompt
            prompt: What does note 7 say?
          - id: a1
            kind: assert
            assertion:
              type: toolCalledAtLeastOnce
              toolName: read_note
          - id: s2
            kind: prompt
            prompt: Thanks, that's all.
          - id: a2
            kind: assert
            assertion:
              type: toolNeverCalled
              toolName: delete_note
    ```

    The rest of the file (`schemaVersion`, `suite`, `target`, `defaults`) is in [Local evals](/cli/local-evals#1-write-a-suite).
  </Tab>
</Tabs>
