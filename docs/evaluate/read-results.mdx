A run page reads top to bottom: how each client and model did, what broke and how to fix it, which cases failed where, and finally what one iteration actually did. Open a run from the **Runs** table on **Overview** or from a suite's run history.

{/* Screenshot: run page for Run #12 of Weather suite, finished, showing the header, two pairing rows, the Findings block and the top of the results matrix */}

## The header

The title reads "Run #N of" and the suite name, for example "Run #12 of Weather suite". Under it, a line counts what the run measured, for example "3 cases · 12 iterations · 2 client-model combos", followed by the server group the run connected.

While any client and model pair is undecided, a pill beside the title says which state it is in: Running, Grading, Pending, Cancelled, Inconclusive or Completed. Pairs that passed or failed get no pill; the rows below show their counts.

| Control | What it does |
|---|---|
| **Compare runs** | Opens a table of every run in the suite. Needs at least two runs. See [Compare runs](#compare-runs). |
| **Run again** | Opens the Set up run sheet to start another run. See [Run a suite](/evaluate/run-a-suite). |
| **Cancel run** | Replaces **Run again** while the run is pending, running or grading, and stops every pair of the launch. |
| **Prompt to improve** | In the "Run actions" menu (⋯). Copies a prompt for your coding agent that describes up to three failing cases: the stage each broke at, the tools expected and called, and a suggested change. |
| **Open failing trace** | In the "Run actions" menu. Opens the failing iteration the page leads with in the case editor, under a "Viewing run · Iteration #N" banner, so you can read its trace next to the case. |

## Pairing rows

Below the header, each client and model pair gets a row: its pass rate, **Passed** and **Failed** iteration counts (plus **Pending** and **Cancelled** when there are any), and **P50**, **P95**, **Tokens** and **Calls**. Once the run has finished, a small arrow beside a number shows how it moved since the previous run of the same pair.

## Findings

The **Findings** block explains the failures. Each finding has two columns, "What broke" and "How to fix", and names the part to change, such as a tool description or input schema.

- **See details** opens "Finding details" with the evidence and the affected iterations; click an iteration to open it.
- **Copy fix prompt** copies that finding as a prompt for a coding agent.
- The arrows page through findings; **See all** opens "All findings".

{/* Screenshot: Findings block with one finding open, showing What broke and How to fix, the See details link, the Copy fix prompt button and the See all pager */}

When no findings have been built for the run, the block falls back to two columns from the run's own results: "What broke" (or "What passed" when nothing failed) and "Next step" (or "How to fix" when a specific fix is known). "There isn’t enough recorded evidence to explain this run." means the iterations recorded too little to analyze; their results are still in the matrix below.

A run that launched several client and model pairs together shows a "Findings for" selector beside the heading. Pick a pair to see its findings.

## Changes since the previous run

Once a run of one client and model pair has finished, a line under the findings compares it with the previous completed run, for example "vs run #11: 1 regressed · 2 fixed · 4 passing". Each case is counted under one word:

| Word | Meaning |
|---|---|
| regressed | Passed in the previous run, fails now. |
| fixed | Failed in the previous run, passes now. |
| still failing | Failed in both runs. |
| passing | Passed in both runs. |
| new | Not in the previous run. |
| removed | In the previous run, not in this one. |
| reconfigured | The case or its evaluation settings changed between the runs, so the two results aren't compared. |

"no case changed state" means every case kept its result.

## The results matrix

The matrix has one row per case and one column per client and model. Each column header shows "x/y iters passed", the p95 latency and the cost.

- **Results** shows each cell's verdict (Pass, Fail, Running or Cancelled), the passed count and a bar split by outcome. **Metrics** shows P50, P95, average tokens and average tool calls per iteration instead.
- "Find a test case…" filters rows by name, and the **Status** filter keeps Failures, Passed, Pending or Cancelled.
- Click a case name to open it in the case editor.
- Click a cell to open that case's averages on that pair and its list of iterations. Click an iteration to open its report.

{/* Screenshot: results matrix with the Results view on, the Status filter set to Failures, and one cell's sheet open listing three iterations */}

### Cost

A dash (—) means no cost was observed, never that the iteration was free. It shows when the model ran on your own provider key, which MCPJam doesn't bill, or when the run reported no token usage.

" · partial" after a cost means only some of that column's iterations were priced. Hover it for the count, for example "3 iterations priced"; "includes runner-reported cost" means part of the total was reported by your SDK runner rather than computed by MCPJam.

## An iteration's report

The report opens on its scorecard. The other tabs show the same iteration as evidence:

| Tab | What it shows |
|---|---|
| Scorecard | Every evaluator, with what was expected and what happened. |
| Steps | The case's steps beside their results. Shown for cases authored as steps. |
| Chat | The conversation as the user would see it. |
| Tool Calls | Each tool call with its arguments and result. |
| Trace | The timeline of turns, model calls and tool calls. |
| Replay | Rendered MCP App views, when the run recorded them. |
| Raw | The recorded data as JSON. |

{/* Screenshot: iteration report on the Scorecard tab with the stage rail open on Tool call and two evaluator rows showing Expected and Actual */}

### The scorecard

Evaluators are grouped by the stage of the [user value chain](/sdk/concepts/user-value-chain) they check: Connection, Discovery, Selection, Tool call, Response and User value. Each row shows **Expected**, the configured criterion, and **Actual**, what the iteration recorded. When an AI explanation exists and is current, **Actual** shows it; otherwise it shows the recorded reason and evidence. "Narrative predates the latest grade." marks an explanation written before the last grade.

Each row carries one state:

| State | Meaning |
|---|---|
| Passed | The evaluator passed. |
| Failed | A required evaluator failed, so the iteration fails. |
| Missed · advisory | An advisory evaluator failed. It is shown, but it does not fail the iteration. |
| Uncertain | A rubric check's answer was too close to even odds to call. |
| Could not be evaluated | The evaluator errored. |
| Skipped / Not applicable | The evaluator did not apply to this iteration. |
| Not measured | Nothing recorded a result. It is not a pass. |

**Configure test case evaluators**, under the scorecard, opens the case's evaluators in the case editor.

### Where the chain broke

When the iteration has a verified chain, a rail on the left lists the six stages, numbered 01 to 06, with a colored dot for each. The scorecard opens on the stage where the chain broke; click any other stage to read it. The open stage's heading says its state, and a failed stage whose rows don't explain the failure shows the chain's own reason under the heading.

Without a verified chain, for example while the run is still going, the stages stack in order instead.

## Compare runs

**Compare runs** opens every run of the suite, grouped by client and model. Each group is a table of runs, with deltas against the previous run of the same pair. A long group shows its first few runs and a button for the rest. The header line gives the suite's pass threshold and how many pairs meet it on the current run, for example "Pass threshold 70% · 2 of 3 settled lanes meet it on #12".

| Column | What it shows |
|---|---|
| Run | The run number. Click it to open that run. |
| Result | Passed, Failed, Inconclusive, Timed out, Running, Completed or Cancelled. |
| Pass | The pass rate, with its change from the previous run. |
| Platform | Where the run was launched from, with the commit when there is one. |
| Date | The run's date and time. |
| P50 / P95 | Median and 95th-percentile iteration latency. |
| Tokens | Tokens used. |

**Back to run** returns to the run page.

## Overview

The Evaluate tab opens on **Overview**, which covers every suite in the project.

- **Suite Health** charts the pass rate of each run for one suite and client, picked from the two selectors, with the suite's threshold as a line and the average across its runs. Click a bar to open that run.
- **Runs** lists every run with the columns Run, Suite, Client, Model, Result, Rate, Platform, Commit, Date, Latency, Tokens and Calls. The **Platform** filter keeps runs launched from the places you check; other filters narrow by suite, client and server.
