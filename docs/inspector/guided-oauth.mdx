The OAuth Debugger walks your MCP server's OAuth 2.1 handshake one step at a time, so you can see exactly which request fails and why. It shows every HTTP request and response, explains each step as you go, and checks your server against the [MCP authorization spec](https://modelcontextprotocol.io/specification/draft/basic/authorization) for the protocol version you pick.

## Getting Started

1. Open **OAuth Debugger** in the sidebar.
2. Click **Edit** next to the server URL to set up the target, prefilled with the selected server. To add a new target without changing the current one, click **Add** instead.
3. Enter your server's base URL and pick a protocol version.
4. Pick a registration method: CIMD, DCR or pre-registered.
5. Click **Continue** to start the flow.

The debugger then walks you through each step of the handshake and explains what happened.

## What the debugger shows

- A step-by-step guide with an explanation of each OAuth step
- The spec versions 03-26, 06-18, 11-25 and 2026-07-28, so you can test against each
- Every registration method: pre-registration, Dynamic Client Registration (DCR) and Client ID Metadata Documents (CIMD)
- Every HTTP request and response, with headers and body
- Tips for common OAuth problems
- A sequence diagram that follows your progress and shows the exact `resource` value the flow sends
- Logs you can copy in guide or raw format

## OAuth trace on the server

When you connect a server with OAuth, MCPJam records every step of the flow, so you can diagnose a failed connection without opening the debugger.

If OAuth fails, a banner on the server card names the step that failed, for example "OAuth failed during Token Request".

For the full trace, open the server's details and expand **Last OAuth Trace**. Failed steps open automatically. The trace shows:

- **Source**: which part of the flow produced the trace (`interactive_connect`, `callback`, `refresh`, or `hosted_callback`)
- **Current step**: the step the flow reached before it finished or failed
- Each OAuth step (discovery, client registration, PKCE, authorization redirect, token exchange), with its status, a message, any error text, and optional HTTP details
- **HTTP History**: every HTTP call in the flow, with tokens and secrets redacted

The trace survives page reloads, so you can read it after the browser returns from the authorization redirect. Disconnecting the server or resetting its OAuth data clears it.

Use the trace to diagnose a real connection attempt, and the OAuth Debugger to walk through the flow step by step against a specific protocol version.

### Reading OAuth log entries

OAuth trace steps also appear in the traffic log. Set the log panel's **Source** filter to **OAuth** to see only them. See [OAuth log entries](/inspector/tools-prompts-resources#oauth-log-entries) for details on the status indicators.

## Bearer token authentication

For an HTTP server that uses a bearer token, the **Auth** tab confirms bearer auth instead of showing OAuth details. Manage or rotate the token in the server's configuration.

The **Auth** tab also shows the server's auth type: **Bearer Token**, **OAuth**, process-based for STDIO, or **No Authentication**.

### Saved bearer tokens

Once a bearer token is saved, the edit form hides it. The **Bearer Token** field reads "Saved — enter a new value to replace".

- To keep the saved token, leave the field blank when you save other changes.
- To replace it, enter a new value and save.

To see the stored token, click **Reveal** next to the **Bearer Token** label. The value is hidden again when you close the panel or navigate away.

## Pre-registered clients

With **Pre-registered** as the registration method, enter a **Client ID** before you save. The pre-registered flow skips Dynamic Client Registration, so it has no other way to get one.

If you save without a Client ID, the form shows an error and opens **Advanced settings** so you can enter it. Switching the **Registration** dropdown to another method, such as **Dynamic (DCR)**, clears the error.

### Pre-registered client secrets

Once saved, a pre-registered client's secret is hidden. The field reads "A client secret is saved" instead of showing an input, and has these controls:

- **Reveal**: shows the stored secret in an editable field. Copy it, or type over it to replace it on the next save. Click **Hide** to close the field without changes.
- **Clear**: deletes the secret when you save. Click **Undo** to keep it.

### Authorization header conflict warning

If you use OAuth and also add a custom `Authorization` header under **Advanced settings**, a warning appears, because OAuth sets that header itself. Remove the custom header, or switch to another authentication method.

## Navigating to the OAuth Debugger from the logger

Hover an OAuth error in the request log and click **Continue in OAuth Debugger**. MCPJam selects the server that produced the error and opens the OAuth Debugger on it.

## Reconnecting OAuth servers

To sign in again, click **Reconnect** on the server card or in the server's details. It's the only control that opens the OAuth consent screen. The server's on/off toggle only reuses existing tokens: if they've expired, it shows a re-authentication error instead.

With [multiple accounts](/inspector/connecting-servers#multiple-oauth-accounts) connected, **Reconnect** in an account's row menu, on the **Config** tab, replaces only that account's token. **Reconnect** on the card replaces the default account's.

## Desktop app behavior

In the MCPJam Desktop app, the authorization step opens in your system browser. After you approve access, a **Continue in MCPJam Desktop** page hands you back to the app, which finishes the flow in the OAuth Debugger. If the handoff doesn't happen, click the link on that page.

## Warnings and strict checks

### Resource indicator warnings

When the server's Protected Resource Metadata (PRM) advertises a `resource` identifier that does not fully satisfy RFC 9728 (for example, a same-origin resource on a different path than the transport endpoint), the debugger logs a warning at the `received_resource_metadata` step and continues the flow. The warning includes the advertised value, the server URL, and whether strict MCP clients (such as Quick OAuth or the official MCP SDK) will refuse to connect.

The debugger carries on so you can see how the server really behaves. For strict RFC 9728 validation, use [OAuth Conformance](/cli/oauth-conformance).

### Path-scoped authorization servers

Some multi-tenant authorization servers (such as Scalekit) scope their OAuth endpoints under a path, for example `https://<env>.example.com/resources/res_x`, while their metadata advertises the origin root as the `issuer`. By default, MCPJam requires the advertised `issuer` to match the URL discovery started from exactly (RFC 8414 §3.3), so those servers fail discovery with an error that names the mismatch and the switch that fixes it.

To connect to a path-scoped authorization server, turn on the **Path-scoped authorization server** switch:

- In the OAuth Debugger, click **Edit** next to the server URL and expand **Advanced settings**.
- In the server form, open **Advanced Settings** in the authentication section.

The switch is off by default and is saved per server, for both the OAuth Debugger and connecting. When it's on, these rules still apply:

- The advertised issuer must be a same-origin, segment-aware path-prefix ancestor of the discovery URL. For example, `/resources` is accepted as an ancestor of `/resources/res_x`, but `/resources-evil` is not.
- The `token_endpoint` and `registration_endpoint` in the server's metadata must stay on the advertised issuer's own origin. A present endpoint that points off-origin is rejected even with the toggle on.
- A query string or fragment on either side of the comparison disqualifies the relaxation (RFC 8414 §2 forbids both in an issuer identifier).
- Cross-origin issuers are always rejected.

When the switch accepts a path-scoped issuer, the OAuth flow log records a warning, because strict MCP clients may still refuse to connect.

### Authorization-response `iss` mismatch warnings

When the authorization server returns an `iss` parameter on the callback that doesn't match the issuer from its metadata, what happens depends on the flow's protocol version:

- 2026-07-28: the flow stops before the authorization code is redeemed. The error names both issuers so you can compare them.
- 2025-11-25 and earlier: the flow continues, and a warning toast names both issuers. These versions don't require issuer validation (RFC 9207).

In both cases the mismatch is recorded on the OAuth trace at the `received_authorization_code` step, visible in the **Last OAuth Trace** panel.

## Good to know

- **Where secrets are stored.** In the hosted app, bearer tokens and client secrets are kept in a secure vault, never in browser local storage. In the local inspector, they're stored in browser local storage with the rest of your server configuration.
- **Revealing a secret.** **Reveal** appears only in the hosted app.
- **Adding a target from the header.** The header's **Add Server** button also opens a blank form without changing the server selected in the debugger.
