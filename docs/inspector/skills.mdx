[Skills](https://agentskills.io/what-are-skills) tell a model how to use your MCP tools and complete workflows. Test them in the Playground, where the model picks skills to fit the prompt, or you add one yourself with `/`. MCPJam finds skills in your filesystem and on connected MCP servers, and you can upload new ones.

## Getting Started

1. Open **Connect** and select the **Skills** tab.
2. Add skills. MCPJam finds them in the [skill directories](#skill-directories) on its own. You can also upload them on the **Skills** tab, or run `npx skills` to install them.
3. Open the Playground. The model picks skills for each prompt, or you type `/` to add one.

## Skill Directories

MCPJam looks for skills in these directories. Each skill is a subdirectory with a `SKILL.md` file. If two skills share a name, the first one found wins.

**Global:**
```
~/.claude/skills/
~/.mcpjam/skills/
~/.agents/skills/
```

**Project-local:**
```
./.claude/skills/
./.mcpjam/skills/
./.agents/skills/
```

<Tip>
  If you have no skills installed, run `npx skills` to get started quickly.
</Tip>

## Uploading Skills

Upload a skill folder from the **Skills** tab by dragging it in or browsing for it. The dialog checks the `SKILL.md` frontmatter as you go.

Uploaded skills are stored in `~/.mcpjam/skills/`.

<Note>
  You can't upload a skill whose name already exists. To replace it, delete the existing skill first.
</Note>

## Updating Skills

To pull the latest version of the `mcp-inspector` skill (which contains MCPJam's guidance for interpreting probe, doctor, OAuth, and conformance output), run:

```bash
npx skills update mcp-inspector
```

To update every installed skill at once:

```bash
npx skills update
```

## Using Skills

### Progressive Disclosure

MCPJam puts a catalog of your skills, each with its name and a one-line description, in the model's system prompt. The model decides which skills fit your prompt and calls `loadSkill` to load just those. Once a skill is loaded, the model can browse and read its supporting files with `listSkillFiles` and `readSkillFile`. A turn with no skills gets no catalog and no skill tools.

#### Catalog Size Limit

The catalog is capped at 2% of the model's context window, counted at about 4 characters per token. If MCPJam doesn't know the model's context length, the cap is 8,000 characters.

If your skills don't fit, MCPJam shortens descriptions first and leaves out whole skills only as a last resort. The catalog says when it left skills out:

```
(3 more skills could not be listed within this model's skill-metadata budget.)
```

The model can't see or load a skill that was left out, so keep descriptions to one line if you have many skills.

### Deterministic Injection

To make sure the model uses a skill, type `/` in the input and select it. MCPJam adds the skill's `SKILL.md` to the conversation before the model reads your message.

The skill appears as a card above the input. Expand the card to browse its files and select any others to include. By default, only `SKILL.md` is added.

## LLM Tool Integration

When at least one skill is available, the model gets `loadSkill`, plus the two file tools where skills can carry supporting files:

| Tool | Description | When advertised |
|------|-------------|-----------------|
| `loadSkill(name)` | Load the full skill instructions by name | Whenever the turn has at least one skill |
| `listSkillFiles(name)` | List all files in the skill directory | Only when the turn's skills can carry supporting files |
| `readSkillFile(name, path)` | Read the content of a specific supporting file | Only when the turn's skills can carry supporting files |

<Note>
`listSkills` appears only when a connected MCP server provides skills through the [Skills over MCP](https://aaif.io/blog/skills-over-mcp) extension (SEP-2640), and it lists only those skills. The model can use it to re-read the catalog mid-conversation.
</Note>

## Skills over MCP (Server-Provided Skills)

If your MCP server serves skills through the SEP-2640 skills extension, MCPJam adds them to the catalog next to your local skills, each labelled with its server (`MCP server "…"`). The model loads them with `loadSkill`, like any other skill.

Before any content reaches the model, MCPJam fetches each file in the skill's manifest and checks its digest, and its byte length when the server gives one.

Both sides have to declare the extension. Turn on **Skills over MCP** on the client's **MCP Protocol** tab. The MCPJam and VS Code clients have it on; other clients start with it off. A change applies on the next connect.

On the **Skills** tab, each server skill shows its server as a badge. A server that hasn't declared the extension shows no skills.

The [stable spec](https://github.com/modelcontextprotocol/ext-skills/blob/main/specification/stable/skills.mdx) targets protocol revision 2026-07-28. MCPJam also sends `skills/*` on a 2025 connection when both sides declared the extension, but without the request `_meta` the spec requires, which only exists on 2026-07-28.

The tab's refresh button reloads your local skills and every server's skills at once.

### Inspecting a server's skills from the CLI

`mcpjam skills` asks a server which skills it serves and verifies them. It
connects directly, so it needs no MCPJam project or API key:

```bash
mcpjam skills list --url https://example.com/mcp
mcpjam skills get --url https://example.com/mcp --uri "skill://acme/refunds/SKILL.md"
mcpjam skills read --url https://example.com/mcp \
  --skill-uri "skill://acme/refunds/SKILL.md" \
  --resource-uri "skill://acme/refunds/scripts/run.py"
```

`mcpjam resources list` also shows `skill://` URIs, but only as bytes, with
no manifest, digest check or explanation when something is wrong. The
`skills` commands verify like the Playground does, so you get either verified
content or a refusal naming the check that failed (see
[Unloadable skills](#unloadable-skills)). A refusal prints to stdout and exits 0.

These commands declare the skills extension on connect. If you pin a host that
doesn't, such as `--host cursor`, the command refuses, because that host would
see no skills:

```
$ mcpjam skills list --url https://example.com/mcp --host cursor
`skills` requires the advertised client capabilities to include the
`io.modelcontextprotocol/skills` extension ... That host would not see this
server's skills at all.
```

Agents driving MCPJam reach the same three operations as `list_server_skills`,
`get_server_skill` and `read_server_skill_file`, over `/api/v1`, the hosted
MCP server, and the in-app assistant.

### Checking that your own server serves skills correctly

`mcpjam server doctor` includes a `skills` check. Unlike the tool, resource
and prompt checks, it fetches a sample of skills and verifies each against its
manifest:

```
- skills: ok (4 skills discovered. 4 verified against their manifests.)
- skills: error (1 of 2 sampled skills failed verification:
  skill://demo/tampered/SKILL.md (digest_mismatch).)
```

It reports `skipped` when the extension isn't active, as for any server that
serves no skills.

It also reports `error` for stable-spec requirements the Playground tolerates:
a `skills/list` or `skills/get` result without `ttlMs` and `cacheScope`, a
listed file without its `size`, or an extension declaration without the
`resources` capability. The doctor's status is then `partial` and it exits 1,
so a CI step that runs it fails until your server sends the required fields.

### Unloadable skills

A server skill can appear in the catalog but be refused for loading. It stays in the catalog marked `unverifiable`, so the model stops retrying it and you can see what the server advertised, but its content never reaches the model. The reason is always shown:

| Reason | What it means |
|--------|---------------|
| `no_resources` | The server omitted the `resources` manifest the spec requires. MCPJam cannot verify the skill's contents without one. |
| `dynamic_resources` | The server declared `"resources": "dynamic"`: a form the spec defines for skills generated per request. There is no manifest to verify against, so MCPJam declines to load it. |
| `too_many_resources` | The skill's manifest lists more than 512 files, which is the per-skill limit the spec requires hosts to support. |
| `too_large` | The skill's manifest declares a total size over 16 MiB, which is the per-skill byte budget the spec requires hosts to support. |

A skill refused with `too_many_resources` or `too_large` isn't a server bug: its manifest is larger than hosts are required to handle.

### Size limit

Verification allows up to 16 MiB per skill, the spec's budget. Separately, one `loadSkill` or `readSkillFile` result can put at most 256 KiB of skill content in a model turn. A skill or file over that cap is refused with `too_large_for_prompt` instead of being cut off mid-sentence.

### While a server skill is loaded

While a server-provided skill's `SKILL.md` is in the conversation, running a shell command (`bash`) or reading a resource from a saved server (`read_server_resource`) always asks for approval, whatever the tool approval setting says. The spec requires this for code execution and cross-server reads driven by skill content. The `read_server_resource` approval shows its input, which names the server being read. With an org provider in the local runtime, which can't resume a turn after an approval, such a turn is refused with `tool_approval_unsupported` instead.

If the server changes a loaded skill's files, `listSkillFiles` and `readSkillFile` refuse with `manifest_changed` until the skill is loaded again, so a file added later is never read as part of the skill you saw.
