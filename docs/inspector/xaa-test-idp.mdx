When you build an MCP resource server (or an authorization server) that accepts Cross-App Access (XAA) identity assertions, you need an identity provider (IdP) you can point it at. MCPJam ships one. The XAA Debugger plays the IdP for you — it mints ID tokens and signs the short-lived Identity Assertion Authorization Grant (ID-JAG) your authorization server redeems via the JWT-bearer grant (RFC 7523).

To make that work, your authorization server has to **trust** MCPJam as an issuer. This page covers the three endpoints you register to establish that trust.

## Where to find the endpoints

Open the **XAA Flow** tab in MCPJam Inspector. At the top of the tab, the **MCPJam is your identity provider** card lists three copy-able URLs. Click **Before you run this test** to open a setup guide that walks you through configuring your authorization server step by step.

## The three endpoints

| Endpoint | What it is | Where it goes |
| --- | --- | --- |
| **Issuer URL** | The `iss` value MCPJam stamps on every assertion. | Register it as a trusted issuer at your authorization server. |
| **OpenID configuration URL** | The `/.well-known/openid-configuration` document. Advertises the issuer, JWKS URI, and supported grant types. | Most authorization servers discover the JWKS automatically from here. |
| **JWKS URL** | The public signing keys (`/.well-known/jwks.json`). | Register it directly if your authorization server doesn't auto-discover from the OpenID configuration. |

## Registering trust

1. **Trust MCPJam's identity provider.** Copy the **Issuer URL** from the card and register it as a trusted issuer at your authorization server. Also copy the **JWKS URL** if your authorization server asks for the key-set endpoint directly rather than auto-discovering it.
2. **Choose how MCPJam identifies the client.** Use whichever option your authorization server supports:
   - **Pre-registration** — Create a client for MCPJam in your authorization server, then enter the returned client ID in MCPJam.
   - **DCR** — Let MCPJam create a client during the test through your registration endpoint.
   - **CIMD** — Let MCPJam identify itself with its client metadata URL (requires CIMD support on your authorization server).
3. **Check exchange support.** Your authorization server must accept an ID-JAG from an external issuer and exchange it using the `jwt-bearer` grant (RFC 7523).

Once trust is established, run the flow from the XAA Flow tab. The sequence diagram shows each step — SSO, token exchange, JWT-bearer, and the authenticated MCP request — with every token decoded inline.

## Vendor notes

- **Okta** — Native JWT-bearer support. Register MCPJam's issuer URL as a trusted issuer; Okta discovers the keys from the OpenID configuration.
- **Auth0** — Supported with configuration. Register MCPJam's issuer as a trusted issuer and map subjects to Auth0 users; Auth0 fetches the JWKS from the issuer's discovery document.
- **Keycloak** — Supports Token Exchange. Configure a brokered IdP that trusts MCPJam's issuer.

## Hosted vs. local issuer

When you enable the **hosted issuer** (`app.mcpjam.com`), ID tokens and ID-JAGs are minted by `app.mcpjam.com`. A cloud authorization server can discover this issuer and fetch its JWKS. No tunnel is needed. Token requests and MCP calls still run from your machine; your authorization server must be reachable over HTTPS.

When running the inspector locally, the endpoint URLs point at your own machine. A cloud-hosted Okta or Auth0 tenant cannot reach `localhost`. Your authorization server can only fetch the local endpoints if it can route to that machine — expose the inspector through a public tunnel first.
