Connect your MCP server and MCPJam tells you, on the server card, how well it will work in each major host. You don't have to run anything.

## The support pill

Once a server is connected, a support pill appears at the bottom of its card, reading "Supported by N" with up to three client logos. ChatGPT and Claude come first when they support the server.

- **Supported**: the pill shows the count and up to three client logos.
- **No supporters**: the pill reads "No clients support this server" in red. While the check runs it reads "Checking compatibility…", and if the check fails, "Compatibility checks unavailable".

A client counts as a supporter when its host profile covers all of the server's relevant requirements. A `works` verdict with a blocking or protocol-mismatch finding doesn't count.

Click the pill for the full breakdown by host on the server's **Clients** tab.

## The Clients tab

The **Clients** tab in the server's details shows, for each host:

- **Verdict**: Works / Degraded / Blocked / Unknown, with a colored dot.
- **Provenance**: How far to trust the host profile. Hover the verdict dot to see whether it comes from a published vendor capability table, was captured from a live client session, or is a best-effort estimate.
- **Findings**: Click the summary line to expand the full list of findings for that host. Each finding shows:
  - A severity icon (blocker, degraded, or info).
  - A title and detail explaining what's affected and why.
  - A remediation hint where one exists, for example "Declare an MCP Apps template alongside the OpenAI one".
- **Test**: Opens the Playground in a new client set up like that host, with your server attached. See [Test in an emulated host](#test-in-an-emulated-host).

## What the report checks

### Widget rendering

Most findings come from here. The report checks whether each host can render the widget bridges your server's tools declare:

- **MCP Apps** (`_meta.ui.resourceUri`), rendered by Claude, ChatGPT, Cursor, and Copilot.
- **OpenAI Apps** (`openai/outputTemplate`), rendered by ChatGPT and Copilot via the `window.openai` shim. Not rendered by Claude or Cursor.
- **Dual-bridge** (both keys declared): renderable wherever either bridge is supported.

When a host can't render a widget, the verdict is **Degraded** (the tool falls back to its plain-text result). If the tool is declared app-only (`_meta.ui.visibility` excludes `"model"`), there is no text fallback and the verdict is **Blocked**.

### Widget capability gaps

For each widget, MCPJam reads its HTML with `resources/read` and looks for the host APIs it calls, such as `ui/message`, `tools/call` or `window.openai.sendFollowUpMessage`. A finding appears only when:

1. A widget in your server actually uses a capability, **and**
2. The host's capability matrix doesn't support it.

So the findings are about your server, not the host in general. If your widget doesn't call `ui/message`, you won't see a "follow-up messages won't work" finding, even on a host that lacks it.

If `resources/read` fails, the capability check stays **Unknown** instead of claiming **Works**.

## Verdicts in detail

### Works

All checks passed. The server's tools, widgets, and declared capabilities are fully supported by this host.

### Degraded

One or more features will be lost, but the server still connects and the model can still call tools. Common degraded findings:

- A widget falls back to plain text because the host doesn't render that widget bridge.
- A widget calls `ui/message` (follow-up messages) but the host doesn't support it.
- A widget calls `tools/call` (server tool calls from within the widget) but the host doesn't support `serverTools`.

### Blocked

The server is unusable in this host. This happens only when a widget tool is app-only and the host can't render it: the model can't see the tool and there's no text fallback.

<Note>
The report doesn't flag transport or auth problems, such as a local stdio server that a cloud host can't reach.
</Note>

### Unknown

The report doesn't have enough information. This happens when:

- The tool list hasn't loaded yet (the pill shows "Checking compatibility…" briefly after connect).
- Every `resources/read` call for the server's widgets failed, so the capability scan couldn't run.

Unknown doesn't mean Works. The report just doesn't guess.

## Provenance and confidence

Host profiles are best-effort. The provenance label on each verdict tells you how much to trust it:

| Provenance | Source | Confidence |
|------------|--------|------------|
| Vendor doc | Published capability table (e.g. Microsoft's Copilot MCP Apps table) | High |
| Probe | Captured from a live client session (e.g. Cursor 3.21.16) | High, but versioned |
| Assumed | Best-effort preset judgment | Lower. Treat as a starting point |

The report comes from static checks, not a live test against the real host. To check behavior, click **Test** and try your server in the Playground.

## Acting on findings

### Fix a degraded widget

If a widget is degraded because the host doesn't render its bridge, the finding includes a remediation hint:

- MCP Apps widget on an OpenAI-only host: add an `openai/outputTemplate` key alongside `_meta.ui.resourceUri` so the tool has both bridges.
- OpenAI Apps widget on an MCP-Apps-only host: add a `_meta.ui.resourceUri` key alongside `openai/outputTemplate`.

After you update your server, reconnect it and the support pill updates.

### Test in an emulated host

Click **Test** next to any host in the Clients tab to:

1. Create a new client from that host's template (Claude, ChatGPT, Cursor, or Copilot).
2. Attach your server to it.
3. Open the Playground with that client selected.

Chat with your server there to check the fix under the host's capabilities and sandbox policy.
