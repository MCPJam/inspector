Pin the inspector to one MCP protocol version to test exactly how your server behaves on it, including the 2026-07-28 stateless RC. By default, connections use **Automatic**: they try `server/discover` for 2026 support and fall back to the older `initialize` negotiation, over both HTTP and stdio. Pins work on HTTP connections only; stdio always uses Automatic.

## Where the setting lives

There are three places to set a version, and they layer:

1. The Client's **MCP Protocol** tab sets the _host default_ for every HTTP server attached to that Client without its own override.
2. **Connection overrides** in the **Add Server** form sets a _per-server override_ when you add a server to a project.
3. **Connection overrides** in a server's configuration sets a _per-server override_ later. A per-server override wins over the host default.

Use the host default to make every HTTP server in a Client speak the same version. Use per-server overrides to test a mix, for example a server pinned to 2025-11-25 next to one you're upgrading to Latest.

## Available versions

### Host default (client-level) dropdown

| Option                    | Stored value       | Transport                                       | Use it when                                                                                                                                 |
| ------------------------- | ------------------ | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **Automatic**             | `"auto"`           | HTTP + stdio: `server/discover`, then legacy fallback | Detect 2026 support from the server; otherwise use the version negotiated by `initialize`. This is the default.                        |
| **Latest (2026-07-28)**   | `2026-07-28`       | HTTP in MCPJam's preview (Streamable HTTP POST) | You want to test your server against the newest stateless revision. No `initialize` handshake, `server/discover` for capabilities, per-request `_meta`. |
| **2025-11-25**            | `2025-11-25`       | HTTP, SSE                                       | Pin to the 2025-11-25 stateful release. The initialize handshake offers only this version.                                                  |
| **2025-06-18**            | `2025-06-18`       | HTTP, SSE                                       | Test against the June 2025 stable revision.                                                                                                 |
| **2025-03-26**            | `2025-03-26`       | HTTP, SSE                                       | Test against the March 2025 stable revision.                                                                                                |
| **Client default** _(per-server only)_ | n/a     | n/a                                               | Inherit whatever the Client's MCP Protocol tab is set to.                                                                                   |

**Automatic** is never sent to the server. The inspector negotiates the version with the server at connect time. Any other option pins the connection to that exact version.

When Automatic falls back to `initialize`, it negotiates only within the client's **Supported protocol versions** list, if set, and rejects a server that offers a version outside it. Without a list, the SDK's defaults apply. For strict control regardless of the list, pin a version.

MCPJam supports the 2026 RC over Streamable HTTP POST only. The per-server dropdown hides the RC for STDIO and legacy SSE servers, and if a host-level RC default reaches a non-HTTP server, the connection fails with a transport error.

When you pin a client to a version that isn't in its own supported protocol versions, a warning appears below the dropdown:

- A stateless pin, such as `2026-07-28`: the warning says the pin has no fallback. It saves, but connections to servers that don't speak that version fail. Pick **Automatic** unless you're testing that version.
- A stateful pin, such as `2025-11-25`: the warning says saving will fail. Pick an advertised version, or add it to `supportedProtocolVersions` in the JSON editor below.

If a per-server override holds a version that isn't one of the dropdown's options, the picker shows **Pinned (…)** so you can see a pin is in effect.

1. Open **Connect**.
2. Pick the Client you want to edit, or create one.
3. Open the **MCP Protocol** tab.
4. In the **Protocol version** dropdown, pick a version:
   - **Automatic**: negotiate the version at connect time (default).
   - **Latest (2026-07-28)**: pin to the newest stateless revision.
   - **2025-11-25**: pin to the 2025-11-25 stateful release.
   - **2025-06-18** or **2025-03-26**: pin to an earlier stable revision.
5. Save.

Every HTTP server attached to this Client now connects with that version, unless it has its own override. Stdio servers keep using Automatic.

## Overriding a single server

You can set the per-server protocol version either when adding a server or when editing an existing one.

### At add time (shared projects)

The 2026 RC option appears only for HTTP servers.

1. Click **Add Server** in the **Servers** tab.
2. Fill in the server details.
3. Expand **Connection overrides**.
4. Pick **Client default**, **Latest (2026-07-28)**, **2025-11-25**, or an earlier stable revision from the **Protocol version** dropdown.
5. Submit the form.

The pin applies once the server is created and connected.

### After adding (edit flow)

1. Go to the **Servers** tab.
2. Open the server card's ⋮ menu and click **Configure**.
3. Expand **Connection overrides**.
4. Find **Protocol version** and pick **Client default**, **Latest (2026-07-28)**, **2025-11-25**, or an earlier stable revision.
5. Save and reconnect the server.

The per-server override wins over the Client's **MCP Protocol** tab. Like the host default, it applies to HTTP servers only.

## OAuth protocol alignment with MCP negotiation

For an HTTP server with OAuth, the **Protocol** dropdown under **Advanced Settings** in the authentication section chooses which OAuth spec version the connect flow uses. The default is **Auto**.

**Auto** stays Auto when you save the server. Each OAuth flow picks one version, in this order, and records it:

1. An explicit OAuth protocol selection.
2. An explicit per-server or host MCP wire pin.
3. The version freshly detected or negotiated with the MCP server.
4. `2025-11-25` when a `401` requires OAuth before the server can provide protocol evidence.

The last case is a fallback, not detection. If a server that requires sign-in up front needs 2026 behavior, select `2026-07-28` explicitly.

Callback checks follow the flow's version. Every version validates `state`. The 2026-07-28 flow also checks a returned `iss` against the authorization server's issuer (RFC 9207); 2025 flows ignore `iss`.

## What changes when you pick Latest (2026-07-28)

If your server already speaks `2026-07-28`, you mostly won't notice. When testing, know that:

- **No `initialize` handshake.** The inspector connects, immediately fires `server/discover`, and uses the result to populate the server card's name, version, capabilities, and instructions.
- **Per-request metadata.** Every request the inspector sends carries `MCP-Protocol-Version: 2026-07-28` as an HTTP header and the same value inside `params._meta["io.modelcontextprotocol/protocolVersion"]`. `clientInfo` and `clientCapabilities` ride along on every request too.
- **No session IDs.** The inspector never sends an `mcp-session-id`. If your server returns one, the inspector discards it and warns you, because that doesn't conform to the stateless RC.
- **Cancellation is closing the stream.** For SSE responses, the inspector closes the response stream to cancel; your server should treat that as a cancel signal.

### What the inspector tells you

- If your server doesn't speak `2026-07-28`, the connection fails with a message naming the server and the pinned version, for example, `MCP server "my-server" doesn't support MCP protocol version 2026-07-28, which this client is pinned to.` The error banner and any connect or reconnect toast have a **Change protocol version** button that opens the client's **MCP Protocol** tab. Set the version to **Automatic** to negotiate whatever the server supports, or pick a version the server advertises.
- If your server is missing a capability the inspector needs for a request, you'll get `-32003 MissingRequiredClientCapability` back from your server. Check the JSON-RPC log to confirm they reach you.
- The JSON-RPC log is the source of truth: every request and response, success or error, lands there so you can verify `_meta` content. See [Tracing & debugging](/inspector/debugging).

### Limits of the RC client

The 2026 RC client is a preview. Two things work differently from the legacy client:

- **Sampling and roots.** The client never advertises either capability, so it rejects a `sampling/createMessage` or `roots/list` request that a server embeds in an `InputRequiredResult`. Elicitation via `input_required` is supported; see [Multi-round input](/inspector/tools-prompts-resources#multi-round-input-mcp-2026-07-28-input_required).
- **Automatic detection.** Over HTTP and stdio, automatic detection falls back to the legacy `initialize` handshake when `server/discover` is not available. An explicit 2026 pin remains exact and does not fall back.

For everything else (`tools/list`, `tools/call`, `resources/*`, `prompts/*`, resource subscriptions over `subscriptions/listen`, OAuth refresh, custom headers, progress notifications), the RC client behaves like the legacy one.

## Recommended testing flow

1. Create a Client, such as `Latest protocol sandbox`, and set its **MCP Protocol** tab's **Protocol version** to **Latest (2026-07-28)**.
2. Attach the HTTP server you're upgrading.
3. Connect, and check that the server card shows the name, version, capabilities and instructions from `server/discover`.
4. Run a `tools/list` and a `tools/call` from the **Tools** tab.
5. Watch the JSON-RPC log for the request `_meta`.
6. Try an unsupported version on a second test server to confirm your `-32004` error envelope looks right.
7. Once your server is happy on Latest, keep one Client on **Automatic** (or pinned to **2025-11-25**) so you can flip between versions without rewriting settings.

If you need to talk to a mix of servers on different versions in the same Client, use per-server overrides: the RC server stays pinned to `2026-07-28`, the other HTTP servers fall back to the host default.

## Good to know

- **Servers pinned to `DRAFT-2026-v1`.** That placeholder is gone, replaced by `2026-07-28`. Select the protocol version again in the inspector. Spec-conforming servers reject the old pin with `-32004 UnsupportedProtocolVersionError`.
