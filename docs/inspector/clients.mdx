A Client lets you test your server the way a real host such as Claude Desktop, ChatGPT or Cursor would use it, before you ship to that host. Each real host advertises different capabilities and sandboxes MCP Apps differently. A Client saves those settings, along with the model, system prompt and attached servers, under one name you pick in the Playground, Studies and Evals.

Because every setting that affects a run lives in the Client, a teammate who picks the same Client gets the same conditions. Manage Clients from **Connect** in the sidebar.

## What you can configure

A Client groups settings into two layers: the protocol layer, which sets how the MCP connection behaves, and the app layer, which sets what an MCP App running inside the client may do.

### Protocol-level settings

These set what the inspector sends in the MCP `initialize` handshake and on every request after it. Most live on the **MCP Protocol** tab.

- **Supported protocol versions**: The ordered list of MCP protocol versions the client advertises. The first entry is sent as `protocolVersion`; the rest form the accept-set. Use it to test how your server handles older or newer clients.
- **`clientInfo`**: The `name`, `version`, and any additional fields sent in `initialize.params.clientInfo`. Set this to match a real host's identifier when you want your server to take a host-specific code path.
- **Client capabilities**: The capabilities object sent in `initialize` (elicitation, experimental, extensions, etc.). Turn each one off to test what your server does when a capability is missing. You can advertise `sampling` or `roots`, but MCPJam never answers `sampling/createMessage` or `roots/list`, so you can't test those flows end to end.
- **Elicitation**: Controls the `clientCapabilities.elicitation` key. Off leaves the key out. On advertises `{ form: {} }`, so your server knows the client can handle elicitation requests. With Elicitation on, **URL mode** also adds `{ url: {} }`, meaning the client can handle requests to open a URL.
- **Mirror tool params into `Mcp-Param-*` headers (SEP-2243)**: **Mirror** (the default) copies a tool argument annotated with `x-mcp-header` into an `Mcp-Param-{Name}` request header on `tools/call`, as MCP `2026-07-28` requires. **Omit** acts like a client that doesn't send these headers, such as a browser client, so you can see what your server does without them. A conforming server answers `-32020 HeaderMismatch`, and MCPJam shows that failure without retrying. The setting applies to the whole client, not per server.
- **Mid-session sign-in**: Four dropdowns that set how the client reacts when a server asks for sign-in on one call, through an HTTP `401` or a ChatGPT-style tool result carrying `_meta["mcp/www_authenticate"]`. Each has an action (**Prompt to sign in**, **Notify**, or **Pass through**) and a trigger that says what counts as a challenge. Changes apply without reconnecting. See [Mid-session sign-in](/inspector/lazy-authentication).
- **Request timeout**: Timeout in milliseconds for every MCP call, such as `tools/call` and `resources/read`. Lower it to check that your server handles cancellation; raise it for long-running tools.
- **Default headers**: Headers sent on every HTTP request, such as auth tokens or tenant IDs.

### Per-server connection overrides

To give one server its own timeout or headers, override them on that server in the project's server list. The other servers keep the Client's defaults.

### Agent behavior

These settings, on the **Agent** tab, control how the model uses tools in a chat.

- **Require tool approval**: When on, the model pauses before each tool call so you can approve or deny it. Some tools don't follow it exactly:
  - Browser and WebMCP page tools follow the chat's tool approval setting instead. With that off, agents can act in signed-in websites without asking. Local browsing also needs browser device permission.
  - Read-only lookups of your own project, the progressive-discovery meta-tools and read-only UI actions never pause.
  - Web search follows the switch.
  - For [workspace tools](/inspector/playground#workspace-tools), reads that open a connection to one of your servers pause unless the saved value is off, and tools that change your project always pause.
- **Respect tool visibility**: Whether the inspector honors the SEP-1865 `_meta.ui.visibility` field. When on, the default for every template except Cursor, tools whose visibility is `["app"]` are hidden from the model. When off, the model sees every tool, like hosts that don't filter by visibility (for example, Cursor 3.4.20).
- **Progressive tools**: `On`, `Off` or `Auto`. On gives the model `search_mcp_tools` and `load_mcp_tools` instead of the full tool list, which saves context for large tool sets. `Auto` decides based on how many tools there are.
- **Built-in tools**: Host-provided tools, such as `web_search`, that the model can use alongside your server's tools. The browser is set up on the **Browser** tab instead.

### Browser settings

The **Browser** tab lets the model use a browser. It has two sections.

**This client** is saved with the Client and applies to every chat and environment that uses it:

- **Browser**: Turn the browser tool on or off for this client.
- **Browser profile**: Pin one of your saved browser profiles. Without one, new chats use your default profile.

**Your browser** holds personal preferences that don't change the Client:

- Grant or revoke permission for the local browser on this machine.
- Manage your saved browser profiles.

#### Browser canvas island

The client canvas shows a **Browser** island with the active profile, or **+ Browser** when the browser is off. Click it to open the **Browser** tab.

### MCP App settings (SEP-1865)

If your server serves [MCP Apps](https://modelcontextprotocol.io/docs/extensions/apps), interactive UIs delivered as `ui://` resources, the Client controls how the inspector renders and sandboxes them. These match the fields a real host advertises in `HostCapabilities` and `HostContext`. For tool-only servers, only the protocol settings matter.

- **Host capabilities**: The set of `HostCapabilities` keys the inspector advertises in the `ui/initialize` handshake. Each host preset reflects that host's published capability subset: for example, the **Copilot** preset advertises only `openLinks`, `serverTools`, `updateModelContext`, and `message`, matching Microsoft 365 Copilot's published Component-bridge table, and omits `serverResources` and `logging`. Use this to verify your app degrades gracefully when a capability it relies on is absent.
- **CSP mode**: `host-default`, `declared`, or `relaxed`. Controls the baseline Content Security Policy the inspector applies to your app's iframe.
- CSP `restrictTo`: Per-directive intersections (`connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains`) that further narrow what the app is allowed to fetch, embed, or set as a base URI. Restrict-only. The inspector never adds an undeclared domain.
- Custom CSP directives: Verbatim source-expression overrides (e.g. `script-src: 'unsafe-eval' 'wasm-unsafe-eval'`) for cases where you need to model exactly what a particular host emits at the browser layer.
- **Permissions mode**: Per-feature toggles for `camera`, `microphone`, `geolocation`, and `clipboard-write`. Choose `resource-declared` (grant what the app's resource metadata asks for), `deny-all`, or `custom` (your own allow map).
- **Display modes**: Which of `inline`, `fullscreen`, and `pip` the inspector advertises in `HostContext.availableDisplayModes`. Test how your app responds when a requested mode isn't available.
- Theme and styles: The CSS variables and font block the inspector injects into `HostContext.styles` so you can verify your app picks up host theming.
- `window.openai` injection: Whether the inspector adds the OpenAI Apps SDK `window.openai` shim to widget HTML. The ChatGPT, Copilot and MCPJam presets turn it on; Claude and Cursor leave it off. Override it on the **Apps** tab. The chip in the host capability matrix shows the current state and whether it comes from the preset or your override.
- **Same-origin app iframe**: On the **Apps** tab, in the sandbox settings. Controls whether the app's iframe shares the sandbox page's origin. When off, the app runs in an opaque origin: `localStorage`, `sessionStorage`, `indexedDB` and cookies all throw, and fetches send `Origin: null`. Claude, Claude Desktop, ChatGPT and Copilot are same-origin, so their presets leave it on. A client whose host hasn't been tested also defaults to on, with a tooltip saying so.

#### Apps tab

The **Apps** tab has two separate capability matrices. A change in one never affects the other.

The `window.openai` matrix sets which `window.openai.*` methods apps using the ChatGPT compatibility shim can see. **Inject window.openai** turns the shim on or off. Expand the method list to turn on only the methods you want. Turning on one method turns the shim on with just that method; turning off the last one turns the shim off.

The `app.*` matrix sets the `app.*` surface for apps using the MCP Apps protocol. **MCP App support** advertises the MCP UI client extension (`io.modelcontextprotocol/ui`). Its rows include:

- **`availableDisplayModes`**: multi-checkbox cluster (`inline`, `fullscreen`, `pip`); unchecking the last mode force-enables `inline`.
- **`widgetDisplayModeRequests`**: tri-state host policy (`accept`, `user-initiated-only`, `decline`) for widget-initiated display-mode requests.
- On/off flags for every `app.*` capability (e.g. `toolInputPartial`, `toolCancelled`, `serverResources`, `logging`, `toolInfo`, `openLinks`, `serverTools`, `updateModelContext`, `message`). Rows that diverge from the selected host preset are stored as sparse overrides.

## Creating a Client

1. Open **Connect** in the sidebar.
2. Click **New Client**.
3. Give it a name (e.g. `Claude Desktop`, `ChatGPT`, `Strict CSP`).
4. Open the focus panel to drill into protocol or MCP App settings.
5. Click **Save**.

The canvas on the left shows the Client as a diagram: the model, attached servers and any per-server overrides. When you switch Clients, the cards that changed flash.

To switch Clients, use the client selector at the top left of each Connect view. It shows the active client's logo, name and position in the list, such as `2 / 3`. Click it to pick another client, or hover a client in the list to delete it. In the Client view, the selector also has a button for adding a client, and its menu has **Add clients**.

## Using a Client

Once saved, a Client appears in the picker at the top of each of these views:

- **Chat**: Drives the model, system prompt, attached servers, and connection settings for the conversation.
- **Studies**: Same as Chat, but persisted as a saved study configuration.
- **Evals**: Every test run inside an Eval uses the selected Client, so results are reproducible across teammates.
- **Swarms**: Goals in the Swarms surface can target any project client, including standalone ones.

Switching the Client swaps the whole configuration at once, with no separate apply step.

### Standalone clients (Swarms-managed)

A client created from Swarms → Clients is standalone: Swarms owns it, and it can't be published as a study. It doesn't appear in the Studies client picker, and selecting it in the Scenarios tab shows **Managed by Swarms** instead of a scenario. To use one client for both Studies and Swarms goals, create it from **Connect** instead.

## Server attachments

A server attachment is a named set of servers from your project. It lets you change which servers a run uses without touching the Client's model or prompt.

### Eval suites

When you create an eval suite, pick a server attachment in the **Servers** section of the create dialog. Every client attached to the suite runs against those servers. To change it later, click the attachment pill in the suite header.

A suite with no attachment shows an amber indicator in its header, and its runs won't start until you pick one.

To create an attachment from the picker:

1. Open the server attachment picker, in the suite create dialog or the suite header.
2. Choose the option to create a new attachment.
3. Enter a name, such as `Production servers`, and check the servers to include.
4. Click **Create**. The new attachment is selected.

### Studies

The **Servers** section on a study's Publish tab shows which project servers the study connects to. Edit the selection there.

With no servers picked, the study shows an amber warning, and its chat sessions have no tools. Changing the client's model or system prompt doesn't change the server selection.

## Managing Clients

From the Clients index page:

- **Duplicate**: Copy a Client when you want a small variant (e.g. `Claude Desktop (strict CSP)`) without rebuilding from scratch.
- **Delete**: Removes the Client. You can't delete the project's last client ("You need at least one client.") or one an eval suite uses ("In use by a test suite."). Detach it from those suites first.

## Sharing across a project

Clients belong to the project, like servers and views. Everyone in a shared project sees the same Clients, and saves sync automatically, so a teammate can reproduce your test conditions by picking the same Client.

## Comparing hosts

The **Compare** view shows several host configurations side by side, so you can spot differences in capabilities, sandbox policies or protocol settings before you ship to a host.

### Opening Compare

Click **Compare** from any Connect view. It's the third tab, after Servers and Client.

### Deep-linking to a specific selection

Append `?hosts=<id1>,<id2>` to the `/host-compare` URL to pre-select a specific set of hosts on load:

```
/host-compare?hosts=host-abc,host-def
```

The URL updates as you toggle hosts on or off. With the default selection, the ChatGPT and Claude presets, the URL has no `?hosts` parameter.

## Best practices

- **Mirror your target hosts.** Create one Client per real host you care about (`Claude Desktop`, `ChatGPT`, your own product) and keep its `clientInfo`, capabilities, and sandbox settings aligned with what that host actually advertises.
- **Test the negative paths.** Build a minimal Client with most capabilities off and a strict CSP. Running your server against it shows assumptions that won't hold on stricter hosts.
- **Pin Evals to a Client.** Select a Client before running an eval suite so the results are reproducible.
- **Duplicate before debugging.** When you're chasing a bug, duplicate the Client first and tweak the copy. Your baseline stays intact for comparison.
- **Share Compare links.** Toggle down to the hosts you care about and copy the URL. The `?hosts=` parameter preserves your selection for teammates.

## Good to know

- **Only project admins can create clients.** Other members see the create button disabled with "Only project admins can create clients."
- **Widgets don't render with a custom capability config.** Widgets render only when `clientCapabilities` advertise `io.modelcontextprotocol/ui` with a `mimeTypes` array that includes `text/html;profile=mcp-app`. A bare `{ extensions: { "io.modelcontextprotocol/ui": {} } }` entry renders nothing. The Claude, ChatGPT, Copilot and MCPJam presets are already correct.
- **An app stops responding after reloading itself.** With **Same-origin app iframe** off, an app that reloads itself loses its message channel, and the Sandbox Stack debug panel shows **channel closed**.
- **Auto-connect is personal.** The **Auto-connect** switch in the Connect header connects every project server in your browser, whatever Client is active. Each eval suite or swarm run picks its servers through its [server attachment](#server-attachments).
