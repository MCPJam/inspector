Test your MCP server by hand: call its tools, read its resources and fetch its prompts, and see every JSON-RPC message between MCPJam and your server.

<Note>
  The Tools, Resources, and Prompts tabs work only while the selected server is
  connected. If it disconnects, they clear and ask you to reconnect.
</Note>

## Tools

Call your tools with your own arguments and check what they return. On the **Tools** tab you can:

- Browse and search your tools, with their descriptions and parameters.
- Call a tool with your own arguments and see the result, including ChatGPT Apps and MCP Apps widgets.
- Answer elicitation requests in a form dialog.
- Answer `input_required` results (MCP 2026-07-28) in the same dialog; the call is retried for you.
- Save tool calls you run often. Saved requests are kept in your browser's local storage.

### Elicitation requests

When a tool sends an elicitation request, a dialog asks you for the input. The form is built from the server's schema and supports the full MCP elicitation subset:

- **Labels and defaults**: fields show the schema `title`, if any, next to the property key. Schema `default` values are filled in.
- **Field types**: strings, numbers, integers, booleans (checkbox), single-select dropdowns and multi-select checkbox lists. Fields with `format: email`, `uri`, `date` or `date-time` use the matching browser input.
- **Validation**: **Accept** checks required fields, numeric `minimum`/`maximum`, string `minLength`/`maxLength`, `pattern` and formats. Errors appear under each field and block submission.
- **Server identity**: the dialog header names the server asking. If the server gives both a name and an ID, both appear; the ID is always shown.
- **Other shapes**: nested objects and other shapes outside the elicitation spec get a plain JSON text box.

**Decline** and **Cancel** skip validation and send that action to the server with no parameters.

### Multi-round input (MCP 2026-07-28 `input_required`)

When a tool call returns an `input_required` result (MCP 2026-07-28 §12), the same dialog collects the input, and the inspector retries the call with your answers. It differs from the older `elicitation/create` flow:

- **Dialog title**: shows "Operation Needs Input" (vs "Elicitation Request" for legacy requests).
- **Dialog header**: reads "[server] needs input to continue" (vs "[server] is requesting information").
- **Several requests in one round**: the dialog asks them one at a time and sends all the answers together.
- **Automatic retry**: the inspector retries the original `tools/call` with your answers, so you don't call the tool again.
- **Decline and Cancel**: send that action to the server, which decides whether to stop or continue.

This works on local connections. Connect the server before calling the tool, because the `elicitation` capability is advertised at connect time.

### OAuth scope step-up on tool calls

When a tool call returns `403 insufficient_scope`, the Tools tab signs you in again for more scopes. It asks for the scopes you already granted plus the ones the server named, and sends you to the authorization server to approve them.

If the challenge names no scope (a bare `Bearer error="insufficient_scope"`), it asks for your granted scopes plus the `scopes_supported` in your server's protected resource metadata, or else the authorization server's.

When you come back from the consent screen, the call runs again on its own, even if the tool isn't marked `readOnlyHint: true`. The client's tool-approval setting still applies. Only the sign-in started from the call can re-run it.

If signing in again doesn't fix the scope error after a few attempts, the Tools tab shows the error instead of redirecting again. The count resets when a tool call succeeds or you open a new browser session.

<Note>
In a hosted project, a step-up reauthorizes your own connection in place. If the call used a connection someone else shared with the project, you sign in with your own account instead, and the earlier call is not re-run: run it again yourself.
</Note>

### Sign-in requested by a tool call

Some servers let you connect and call public tools without signing in, and ask for sign-in only when a protected tool runs. They signal it with an HTTP `401` and a `WWW-Authenticate` header, or, ChatGPT style, with an `isError` result carrying `_meta["mcp/www_authenticate"]`.

What the Tools tab does depends on the client you are emulating:

- **Prompt to sign in**: a **Connect** card replaces the error. Nothing happens until you click **Connect**. After you sign in, the call runs again on its own, for read and write tools alike, under the client's tool-approval setting.
- **Notify**: the call fails with a sign-in message. You can sign in from the card, then run the tool yourself.
- **Pass through**: the challenge shows as an ordinary error, with a note on how the emulated host handles it.

See [Mid-session sign-in](/inspector/lazy-authentication) for the per-host settings, the Connect card, and how to test your server with the CLI.

## Resources

On the **Resources** tab you can:

- Browse your resources, with their names, URIs and MIME types.
- Read a resource and see its content.
- Fill in a resource template's parameters and read the result.
- Answer `input_required` results (MCP 2026-07-28) in the elicitation dialog; the read is retried for you.

### Subscription stream panel

The **Subscriptions** panel at the bottom of the Resources tab lets you watch and control your server's subscription streams. It appears only in the local inspector, while a server is connected.

What it shows depends on the protocol version:

**Modern era (`subscriptions/listen`, MCP 2026-07-28)**

The server holds one `subscriptions/listen` stream. A stream's filter can't change, so changing the filter closes the stream and opens a new one. The panel shows:

- **Desired filter**: checkboxes for `tools/list_changed`, `prompts/list_changed` and `resources/list_changed`, plus a watch toggle for each resource.
- **Stream details**: status (`Opening`, `Active`, `Closed by server (graceful)`, `Connection lost (remote close)`, `Cancelled locally`, `Error`), the MCP subscription id and whether it was `reported` or `observed`, the requested filter next to the acknowledged filter, any interests the server did not honor, the close reason, and the re-listen attempt count.
- **Cancel stream**: ends the current stream as a local abort.

**Legacy era (`resources/subscribe`)**

The server subscribes one URI at a time. The panel shows the same stream details, with **Subscribe** and **Unsubscribe** buttons for each URI instead of the filter checkboxes. They call `resources/subscribe` and `resources/unsubscribe`.

**History**

A history log below the streams records each change:

| Entry kind | Meaning |
|---|---|
| `opened` | A new stream was requested |
| `acknowledged` | The server confirmed the filter |
| `reconnected` | A re-listen attempt was made |
| `closed-graceful` | The server closed the stream gracefully |
| `closed-remote` | The connection was lost (remote close) |
| `cancelled` | The stream was cancelled locally |
| `error` | The stream ended with an error |
| `notification` | A subscription notification arrived |
| `rejected` | A notification arrived for an interest the server did not agree to send |

Graceful and remote closes are always separate entries. Rejected notifications are listed, not dropped.

## Prompts

On the **Prompts** tab you can:

- Browse your prompts, with their descriptions and parameters.
- Fetch a prompt with your own arguments.
- Answer `input_required` results (MCP 2026-07-28) in the elicitation dialog; the fetch is retried for you.

To use a prompt in the Playground, type `/` and pick it.

## JSON-RPC Logging

Every message between MCPJam and your MCP server is logged as it happens: full JSON-RPC requests and responses for tool calls, resource reads, prompt fetches and the rest, with errors and timestamps.

### Inline HTTP headers

Expand a request you sent to the server, and an **HTTP headers** section appears below the JSON body. Expand it to see the full HTTP exchange: request headers, response status, and any `Mcp-*` headers the server mirrored back.

Even collapsed, the row names the first mismatch, for example `mcp-name disagrees with the body`, so you can see which header broke routing. It turns red when the exchange returned a 4xx or 5xx status or the connection failed.

`Mcp-Param-*` headers are checked too, when the log holds a `tools/list` for the tool. Each mirrored argument shows ✓ when the header matches the request body, and a failure when it disagrees, is missing, or names a parameter the tool never declared. If the tool's schema isn't in the log, the row says `unchecked — tool schema unavailable`.

The section doesn't appear when the request can't be matched to an HTTP exchange, or when the exchange has no `Mcp-*` headers to check, as on protocol versions before 2026-07-28.

To see every HTTP exchange, including ones without a single JSON-RPC message, set the traffic log's **Source** filter to **HTTP**.

### OAuth log entries

When a server uses OAuth, each step of the flow appears in the traffic log next to the JSON-RPC messages. Set the **Source** filter to **OAuth** to see only those steps.

Each OAuth log entry displays a status indicator:

| Indicator | Meaning |
|-----------|---------|
| `oauth ✓` | Step completed successfully |
| `oauth ✗` | Step failed |
| `oauth …` | Step is in progress |
| `oauth ↺` | Step failed but was recovered (for example, after re-registering the client) |

Click any entry to expand it and inspect the full step payload, including HTTP request and response details.
